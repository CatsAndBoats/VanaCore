# VanaCore reference

Everything VanaCore does, setting by setting. For what VanaCore is and how to build it, see the [README](../README.md).

## Layout
| Path | Builds | What it is |
|------|--------|-----------|
| `src/launcher/` | `VanaCore.exe` | Logs in to the CatsEyeXI server (`login.cpp`), then starts itself again as the game's process, suspended, loads `VanaCore.Core.dll` into it, calls `VanaCoreInstall`, then resumes it (or does the same for a bootloader or any other program) |
| `src/core/` | `VanaCore.Core.dll` | Runs inside the game: hooks, services, plugin and addon hosts |
| `src/shared/` | — | Headers used by both (`BootInfo` handed from launcher to core, the version) |
| `src/gfx/` | `VanaCore.Gfx.lib`, `VanaCore.GfxTest.exe` | Direct3D 8 on Direct3D 12 for `[graphics] renderer=d3d12` (and on Direct3D 11 for `d3d11`: `gfx_d3d11.c`, VanaCore's own), linked into VanaCore.Core: ported from xi-on-mac (`d3d8.c`, `gfx_d3d12.c`, `gfx_hlsl*.c`, marked `VANACORE` where they differ), with `native/` standing in for its recompiler runtime; `test/` holds its offscreen tests, whose Direct3D 8 ones also run on `renderer=d3d9` (`src/core/d3d9.cpp`) |
| `addons/` | — | VanaCore's own Lua addons (`addons/vanacore/`), copied to `build/<Configuration>/addons/` by the build |
| `scripts/` | — | The default `boot.txt`, copied to `build/<Configuration>/scripts/` when there isn't one there (a player's own is never replaced) |
| `tools/gen_ashita_abi.py` | — | Generates `src/core/compat/ashita/abi.hpp` (the Ashita plugin interfaces, 4.16 and 4.30) from the Ashita SDK's headers, and the test plugin that checks it (`--test`) |
| `tools/gen_ashita_gui.py` | — | Generates ImGui for Ashita from the 4.16 SDK's `IGuiManager`: plugins' (`src/core/compat/ashita/gui_v416.inc`) and addons' (`src/core/lua_imgui.inc`) |
| `fonts/` | — | Fonts loaded into the game, copied to `build/<Configuration>/fonts/` by the build: Material Symbols (VanaCore's icons), and `imgui/` (ImGui's: Agave and Font Awesome, as Ashita has them) |
| `third_party/` | — | LuaJIT's source (`luajit/`, with the changes in `luajit-vanacore.patch`) and `build-luajit.cmd`, which builds it for VanaCore.Core; Dear ImGui (`imgui/`, 1.81 WIP, VanaCore's settings in `imconfig.h`), built into VanaCore.Core; NVIDIA's DLSS SDK (`dlss/`, fetched) and AMD's FSR SDK's headers (`fsr/`, its DLLs fetched), for the helper |
| `build-release.bat` | — | Builds Release and puts together a player's VanaCore folder (see Build) |
| `plugins/vanacore/` | — | Empty in the repository: Ashita plugins a distribution ships with VanaCore go here before `build-release.bat` |
| `LICENSE`, `LICENSING.md` | — | VanaCore's licence (GPL-3.0-or-later with additional permissions), and which licence covers which file |

## Build
Visual Studio 2022 or 2026 with **Desktop development with C++** (v143 toolset). Open `VanaCore.sln` and build **x86**: everything is 32-bit because FFXI is. The C runtime is linked statically, so players need no VC++ redistributable.

```
msbuild VanaCore.sln /p:Configuration=Release /p:Platform=x86
```

Output goes to `build/<Configuration>/` (`VanaCore.exe` and `VanaCore.Core.dll` side by side). The build also builds LuaJIT, as a static 32-bit library with the same static C runtime, into `build/obj/luajit/<Configuration>/` (`third_party/build-luajit.cmd`), whenever one of its sources is newer than the library.

NVIDIA's DLSS SDK isn't in the repository (its licence allows it only inside an application): the DLSS helper's build fetches it from [NVIDIA/DLSS](https://github.com/NVIDIA/DLSS) the first time, with `third_party/dlss/fetch-dlss.ps1`, which checks every file's SHA-256 (see `third_party/dlss/README.md`). AMD's FSR SDK's headers are (`third_party/fsr/`, MIT); its signed DLLs (28 MB) aren't: the helper's build fetches them from [AMD's FSR SDK](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK) the same way, with `third_party/fsr/fetch-fsr.ps1` (see `third_party/fsr/README.md`).

### A release
`build-release.bat` builds Release and puts together a player's VanaCore folder in `build\package\VanaCore`: `VanaCore.exe` and `VanaCore.Core.dll`, the DLSS and FSR helper with NVIDIA's and AMD's DLLs in `dlss\`, `vanacore.example.ini` (the launcher makes `vanacore.ini` from it), the default `scripts\boot.txt`, VanaCore's own `addons\`, `fonts\`, whatever is in `plugins\vanacore\`, VanaCore's `LICENSE.txt` and `LICENSING.md`, and `THIRD_PARTY_NOTICES.md` with the `licenses\` it names; the debug symbols go apart, to `build\package\symbols`. It's made from the build and the repository, never from `build\Release\`, which may hold a test run's files. It copies nothing anywhere else: a distribution's own release script copies, signs and publishes the package.
```
build-release.bat
```

On GitHub, **VanaCore Release (vcdev)** (`.github/workflows/release.yaml`, run from the Actions tab) does the same on a Windows runner, signs it and pushes it to the vcdev build on R2 (the test build: testers set the launcher's custom game build to `vcdev`), and makes a draft GitHub release, `VanaCore <version>` with `VanaCore-<version>.zip` and the changes since the last release. The version is `src/shared/vanacore/version.hpp`'s as it is; a version already released isn't pushed again. **VanaCore Promote** (`.github/workflows/promote.yaml`) then copies vcdev's files to the vanacore build every player gets and publishes that draft, tagged `v<version>`, as the latest release.

## Run
Everything comes from `vanacore.ini` next to `VanaCore.exe` (see `vanacore.example.ini`). Relative paths in it are from `VanaCore.exe`'s folder.
```ini
[client]
pol=C:\Games\MyServer\Game\PlayOnlineViewer
ffxi=C:\Games\MyServer\Game\FINAL FANTASY XI

[server]
server=server.catseyexi.com
user=myname
password="my password"
```
```
VanaCore.exe                          # logs in with vanacore.ini's [server] and starts the game
VanaCore.exe --server S --user U --password P --lang US   # as the CatsEyeXI launcher starts it
VanaCore.exe <executable> [args...]   # any other program, with VanaCore.Core loaded
```
`--server`, `--user` (`--username`), `--password` (`--pass`) and `--lang` (`JP`, `US` or `EU`, or `0`-`2`: PlayOnline's region, `US` by default) take the place of `[server] server=`, `user=` and `password=`. The core logs to `logs\vanacore.log` next to `VanaCore.exe` (and `OutputDebugString`).

### Login
VanaCore logs in itself, as xiloader 2.1.2 does, and starts the game without a bootloader. `VanaCore.exe` sends the username and password to the login server (port 54231, TLS through Windows' own Schannel; the server's certificate is self-signed and isn't checked) and gets back the account and a session hash (`Logging in to server.catseyexi.com as myname...`, `Logged in.`). If the server refuses (wrong username or password, a suspended account, already logged in, or a message of its own) or can't be reached, VanaCore says why on its console and in a message box ("Please try again from the CatsEyeXI launcher") and closes, with exit code 3 (refused) or 4 (the server couldn't be reached, or its reply made no sense), without waiting for a key.

Logged in, it starts itself again as the game's process (`VanaCore.exe --vanacore-game`, large-address-aware, with `VanaCore.Core.dll` loaded before anything runs), and VanaCore.Core (`src/core/loader.cpp`) starts the game there: it points the game's `ffxi00.pol.com` at the server and PlayOnline's profile server, `pp000.pol.com`, at its stand-in on this machine, and stamps the session hash into the lobby's requests (winsock hooks on PlayOnline's and FFXI's imports), keeps the lobby's data link to the server (port 54230: the account, the key and the character list), stands in for PlayOnline's profile server on this machine, sets polcore up as the PlayOnline viewer would, and starts FFXI (`FFXiEntry::GameStart`), which returns when the game closes. If PlayOnline or FFXI can't be started, the reason is on the console and in the log, and VanaCore exits with code 5.

Left out on purpose, as the CatsEyeXI launcher does them: xiloader's menus, account creation, password changes, one-time passwords (2FA) and trusted computers (2.1's trust token fields are sent empty), the `--json` file, the hairpin fix, and 2.2's PlayOnline profile relay (friend lists; the server doesn't have it). An account with a one-time password can't log in through VanaCore. From 2.1.2 it keeps the English text for a taken character name. VanaCore reports version 2.1.2: a LandSandBoat login server checks major.minor, and wants 2.1.x from 2026-02-12 (before, 2.0.x; from 2026-09-27, 2.2.x). `[server] loginversion=` (e.g. `2.0.1`) reports another version, for a server that wants one; the server only checks the number (`Reporting login version 2.0.1 ([server] loginversion).`).

`[client] bootloader=` starts a bootloader (xiloader) instead, as before: then `[server]` becomes its `--server`, `--user` and `--password`, other arguments go to it, and it starts in its own folder.

### Retail
`[client] retail=1` (or `VanaCore.exe --retail`, for one start without the setting) starts the retail game the way Windower does, and VanaCore's login, `[server]` and bootloader are not used. `VanaCore.exe` finds PlayOnline in the registry (`HKLM\SOFTWARE\PlayOnlineUS\InstallFolder`, or `PlayOnlineEU`, or JP's `PlayOnline`; the 32-bit view; value `1000` is PlayOnline's folder, `0001` FINAL FANTASY XI's), starts its `pol.exe /game eAZcFcB` suspended (the argument turns on FFXI's quick start button), loads `VanaCore.Core.dll` into it and resumes it. PlayOnline's login and Play button take it from there, and FFXI loads in the same process, so VanaCore's features apply to it as to any other client (`docs/retail-signatures.md` says how its code compares with CatsEyeXI's).
- `retail.region=` (`jp`, `us` or `eu`): which install; by default the first the registry has, US then EU then JP. `retail.args=`: pol.exe's arguments (`/game eAZcFcB` unless set). `retail.pol=`: PlayOnline's folder in place of the registry's (not `pol=`, the CatsEyeXI client's, which retail ignores along with `ffxi=`).
- pol.exe asks for administrator rights in its manifest. When `VanaCore.exe` has none, Windows is asked for them (a second window, which carries on from there) and the exit code is the elevated copy's.
- PlayOnline's windows are titled "PlayOnline Viewer Ver.1.18.15e - VanaCore v0.8.147" (VanaCore looks at them once a second), so you can see VanaCore is in them; `retail.title=0` leaves the titles alone.
- With `attached=0` `VanaCore.exe` exits once PlayOnline has started, as the game is up much later; `attached=1` stays, shows the log, and closing it closes PlayOnline.
- The game keeps the machine's own registry keys and folders: no stand-ins under `HKCU\Software\VanaCore\Registry`, no `pol=`/`ffxi=` redirect of the COM classes, no launcher defaults for settings. `[ffxi]` and `[ffxi.registry]` serve only the settings they name (a window mode `[ffxi] mode` doesn't set is the real registry's), and CatsEyeXI's own DATs (pivot's `catseyexi`) aren't used.
- Not done yet: starting through Steam, running without administrator rights (Windower runs pol.exe as the invoking user and fixes the permissions instead), and several clients at once (PlayOnline's own mutexes).

The game's process shares VanaCore's console. `[client] attached=` decides how long VanaCore stays:
- `attached=0` (default): VanaCore stays through the game's start, so its errors stay readable, then exits once the game is up (its Direct3D device exists) and leaves the game running. The game's process shares VanaCore's console, so at that point it also lets go of the console: the window closes (or a terminal gets its prompt back) and closing it can't end the game. A bootloader's console output after that goes nowhere; `attached=1` keeps it.
- `attached=1`: VanaCore stays with the game and its window shows VanaCore.Core's log live (`VanaCore: ...` lines). The game is in a job object that Windows ends with VanaCore, so closing VanaCore however it closes (its window, Ctrl+C, Task Manager, a crash) closes the game.

If the game exits while VanaCore is still there, VanaCore returns its exit code. When nothing else is attached to the console then (VanaCore was double-clicked or started from a shortcut), it asks for a key before closing the window, so errors from VanaCore or the bootloader stay readable. With `[client] autoclose=1` it closes straight away when the game exits normally (exit code 0), and still asks after an error or a crash. From a terminal it doesn't wait for a key, and with no console window (e.g. a launcher's `CreateNoWindow`) it never does. Each line goes to the shared console in one write, so VanaCore's and the bootloader's lines don't interleave.

`[client] defaults=` is VanaCore's own: how many of its default changes the settings file has had. When a setting's default changes, a file that saved the old default has it taken out once at the next start, so the new one applies, and this goes up; a value set again after that stays. 1: `[graphics.effects] sun_near` 25 to 50.

`password=` is stored in plain text. The CatsEyeXI launcher passes the password on VanaCore's command line, and VanaCore passes it on a bootloader's; VanaCore never logs or prints a command line.

### Log and crash dumps
Logging is **on by default**. With `enabled=0` (the /vana window's **Client > Developer > Logging > Enable logs**, or `/vana logs on` / `/vana logs off`, or `/vana logs` alone to switch it: all of them apply at once, without a restart, and write the key to `vanacore.ini`; what starts with the game, crash dumps and the DLSS helper's log, follows at the next start) VanaCore logs, prints and dumps nothing: no `logs\vanacore.log`, no log lines in the console with `attached=1`, no `OutputDebugString`, no crash dump or report, no DLSS helper log (`logs\dlss.log`) and no `drawlog`. The two things you ask for by name are the exception, and are kept whether or not logging is on: `/vana debug`'s `logs\frames-*.csv` and `logs\debug-*.log`, and `/vana abtest`'s `logs\abtest-*.log` (what you asked for isn't a log of what VanaCore does on its own). What the game, VanaCore.exe's own console messages (the welcome, a failed login) and the programs it loads print or write themselves are theirs, not VanaCore's log.
```ini
[logging]
enabled=1     ; 1: logs\vanacore.log and the rest below (default); 0: nothing is logged
crashdumps=1  ; 0 one line, 1 full report and a .dmp (default), 2 as 1 with all of the game's memory
frametimes=0  ; 1: a line every 10 seconds on where frames go (default 0)
gpu=0         ; 1: with renderer=d3d12, which pass and operation the graphics card stopped at (default 0)
mouse=0       ; 1: the game's cursor and window calls and its mouse messages, up to 3000 lines (default 0)
zoneload=0    ; 1: each zone change's timeline in logs\zoneload-<time>.log (default 0)
```
Each has its own switch under **Client > Developer > Logging**; all but `enabled` and `zoneload` (from the next zone change) apply from the next start. `zoneload=1` writes one file a zone change: the zone-out and zone-in packets in hex, the game's packets in the 5 s before the zone-out and every one it sends while it waits for the server, the data files the zone and its people read, and the frames' gaps. The launcher no longer writes `crashdumps` at each start (Ashita's Enable Crash Dumps checkbox is Ashita's own). Chat logs are a separate switch, **Game Options > Chat > Save chat logs** (`[client] chatlog`).
With `frametimes=1` the log gets a `Frames:` line every 10 seconds: frames per second; frame times (average, fastest-slowest); and in the average frame, the game's own work, the game's `Sleep` calls on the render thread (per module: how many, the ms asked for and the ms actually slept), VanaCore's work, VanaCore's frame rate limit and the device's `Present`. A sleep that lasts much longer than asked (15.6 ms for a `Sleep(1)`) is Windows' default timer resolution at work: see `timer.resolution`.
With `crashdumps=1`, a game crash adds to the log its registers, the call stack (`#0 FFXiMain.dll+0x1234 #1 ...`), code addresses found on the stack (return addresses the walk can miss), and every non-Windows DLL with its path, base address, size and build time; and writes `logs\crash-<date>_<time>-pid<id>.dmp` for Visual Studio or WinDbg: threads, stacks, handles, memory map, the DLLs' code (FFXiMain.dll's as decrypted in memory) and data, and the memory they point at, typically 15–40 MB. `crashdumps=2` puts all of the game's memory in the dump instead (hundreds of MB). A separate thread writes the report, so a stack overflow still gets one. Crashes Windows ends on the spot (heap corruption, security-check failures) skip every in-process handler; VanaCore.exe still logs their exit code if it's there to see it. The game's own teardown after `/shutdown` faults every time, after the game looks closed: for two minutes after a `/shutdown` a fault gets one `Shutdown:` line in the log and no report or dump. The DLSS helper (`dlss\VanaCore.Dlss.exe`, DLSS's, FSR's and frame generation's) reports its own crashes the same way, into the same log, with `crashdumps` from the game: `[VanaCore.Dlss.exe] CRASH:` lines with what crashed and where (`nvngx_dlss.dll+0x1A2B3C`), what the helper was doing (`running DLSS 5, pass 1 of 2`, and the game's frame), its registers, the call stack, code addresses on the stack, its graphics device lost first if it was (a driver timeout), NGX's last message, the card, and every non-Windows DLL with its version (NVIDIA's DLSS DLLs, the graphics driver's), then `logs\dlss-crash-<date>_<time>-pid<id>.dmp`; it then ends with the crash's code, without Windows' "has stopped working" box. The game's own line for losing it says what it was doing too (`DLSS: the helper was running DLSS 5, pass 1 of 2 (the game's frame 4567) when it was lost`), from memory the two share, so that's there even when Windows ended the helper on the spot (a fail-fast, heap corruption), before it could report.

Everything goes to `logs\vanacore.log` next to `VanaCore.exe`: VanaCore.exe's own lines (marked `[VanaCore.exe]`: start, what it launched, errors, how the game exited) and VanaCore.Core's from inside the game. Both append to the one file, each line in a single unbuffered write, so the lines don't mix and are on disk even if a process dies straight after. Look for:
- `CRASH: the game crashed: access violation (0xC0000005) at FFXiMain.dll+0x1234 reading 0x00000010 (thread 123)`: VanaCore.Core's crash handler, which runs before any handler the game sets (it hooks the game's `SetUnhandledExceptionFilter`) and then passes the crash on to it. VanaCore.exe also reports the game's crash exit code, and then exits with 1.
- `The game process is exiting`: a normal exit. Missing after a crash.
- `VanaCore.exe is from a different build`: VanaCore.exe and VanaCore.Core.dll don't match; copy both from the same build.

### Game files
`[client] pol=` and `ffxi=` say which PlayOnline and FFXI folders the game runs from:
- **COM classes**: the bootloader, polcore, FFXi.dll and the rest start each other through COM (`CoCreateInstance`). For PlayOnline's and FFXI's classes (POLCoreCom, PolAppCom, PolContentsCom, FFXiEntry, FxFileManager, GameMain, FFXiVersion), VanaCore loads the DLL from these folders instead of wherever Windows has them registered. A class whose DLL doesn't load falls back to Windows, and the log says why. If Windows has none registered either (usually so on a player's machine), the error reported is the DLL's own (a missing file, a missing function, a failing start-up), not Windows' "class not registered" (0x80040154).
- **Install paths**: `InstallFolder\1000` (PlayOnline) and `\0001` (FFXI) read as these folders, which is where the game finds its DAT files.

The log shows what came from where (`Game files: GameMain from ...\FFXiMain.dll`, `Install folder 0001 = ...`). Without `pol=` and `ffxi=`, everything comes from the PlayOnline install Windows knows about.

(Not with `[client] retail=1`, which leaves the machine's own keys alone: see Retail above.) VanaCore keeps its own PlayOnline registry keys, so no PlayOnline install or registry entries are needed, and one on the machine (retail, or another server's) neither affects the game nor is changed by it. When the game opens one of a PlayOnline install's keys under `HKLM\SOFTWARE\PlayOnline[US|EU]` (the root, `InstallFolder`, `Interface`, `Product`, `SquareEnix\FinalFantasyXI`, and `SquareEnix\PlayOnlineViewer` with its `Settings`, `Settings\Controler`, `SystemInfo` and `SystemInfo\QCheck`; JP's `SQUARE` too), it gets VanaCore's stand-in, whether or not the registry has the key: the key of the same name under `HKCU\Software\VanaCore\Registry\PlayOnline[US|EU]\...`, made the first time, which needs no admin rights. The game reads through a stand-in like any key: `[ffxi]` and `[ffxi.registry]`, `[language]` and the install folders first, then whatever the game has written to it, then a normal install's value (`kStandInValues` in `registry.cpp`, from the CatsEyeXI launcher's reference `ffxi.reg`). Any other PlayOnline key is the registry's own, so one that isn't there is still missing, as it would be with PlayOnline installed. The log names each stand-in the first time (`Registry: HKLM\SOFTWARE\PlayOnlineUS\SquareEnix\FinalFantasyXI is VanaCore's stand-in, HKCU\...`) and each normal install's value it serves.

### Pivot (file overlays)
Mods for the game's files, kept in folders of their own rather than copied over the game's, as XIPivot does them for Ashita:
```ini
[pivot]
enabled=1          ; default 0
rootfolder=pivot   ; the folder holding the overlays (default pivot, in VanaCore's folder)
log=0              ; 1 logs every file served from an overlay (default: the first 20)

[pivot.order]
0=ffxi-hd
1=ffxi-maps\1024x1024
2=catseyexi
```
Each overlay is a folder laid out like the FFXI folder: `catseyexi\FTABLE.DAT`, `catseyexi\ROM\1\45.DAT`, `catseyexi\sound9\win\music\data\music067.bgw`. When the game reads a file in the FFXI folder, the overlays are looked in lowest number first and the first one with the same file serves it; with none, the game gets its own. With the order above, `FTABLE.DAT` comes from `ffxi-hd\FTABLE.DAT` if it's there, else `ffxi-maps\1024x1024\FTABLE.DAT`, else `catseyexi\FTABLE.DAT`, else the FFXI folder's.

Unlike XIPivot, which only sees the `ROM*` folders' DATs and the sound files, any file works: the root `VTABLE.DAT` and `FTABLE.DAT` too (so a mod that adds DATs brings its own tables), and folders the FFXI folder doesn't have (`ROM11\`).
- Paths match however the game spells them (`FINAL FANTASY XI//ROM/1/45.DAT`, either slash, any case). An overlay is a folder under `rootfolder`, or an absolute path (`3=E:\mods\xi-view`); one that isn't there is logged and skipped.
- Reads only: a file opened for writing (the game's `USER` settings) is always the FFXI folder's, and the log says so when an overlay has it.
- The overlays are listed when the game starts, and again a moment after `[pivot.order]` changes (the /vana Pivot tab) or files come and go under `rootfolder`: the files the game opens from then on, such as a zone's DATs at the next zone, come from the new list. What it loads once, at start, keeps the old files until a restart. `[pivot] enabled` and `rootfolder` are read at start only.
- `catseyexi`, the server's own overlay, is always used last when `rootfolder` has it, wherever `[pivot.order]` puts it and whether or not it's listed. The Pivot tab shows it locked.
- It covers the game (`FFXiMain.dll`) and every other DLL that isn't Windows' own: plugins, addons (`io.open`), and VanaCore's own DAT lookups, so the Ashita resource manager's `GetFilePath` gives the overlay's file. A plugin that opens files through Windows' C runtime (`ucrtbase.dll`) gets the game's own.

The log shows each overlay (`Pivot: 2=catseyexi: 318 files (...)`, and how many of its files an overlay before it already has), the FFXI folder once the game loads (`Pivot: the game's files under ...\FINAL FANTASY XI\ come from the overlays first`), and the first files served (`Pivot: FTABLE.DAT from catseyexi`).

### Game settings
The game's own settings (the ones FINAL FANTASY XI Config sets: resolutions, graphics, sound, the gamepad) come from `[ffxi]`, by name. When the game reads a value from its settings key (`HKLM\SOFTWARE\PlayOnline[US|EU]\SquareEnix\FinalFantasyXI`), it gets the one `[ffxi]` sets for it instead of the registry's: `resolution.game=1920x1080` is `0001` and `0002`, `mipmap=6` is `0000`. A setting that isn't set gets its default, a new account's in the CatsEyeXI launcher; one without a default, or set to `-1`, keeps the stand-in's own value (above). One that isn't a number where a number goes is logged and ignored (`Game settings: [ffxi] mipmap=high isn't a whole number; ignored`), and a number outside what a setting is known to take is logged and still handed to the game. VanaCore never reads or changes a PlayOnline install's registry, so other programs and FFXI installs keep their own settings. Each value the game reads is logged once, with where it came from (`Game setting 0001 = 2560 ([ffxi] resolution.game)`, `Game setting 0000 = 6 ([ffxi] mipmap's default)`). The launcher writes the account's settings here.

| Key | Registry values | Default | Effect |
|-----|-----------------|---------|--------|
| `registry.override` | | `0` | Which wins where `[ffxi]` and `[ffxi.registry]` both set a value: `0` `[ffxi]`'s, `1` `[ffxi.registry]`'s (for `mode` too, against its `0034`) |
| `resolution.game` | `0001`, `0002` | the main display's resolution | The game's resolution, `1920x1080`: what it lays its screen out in (with `renderer=d3d8` or `d3d9` in full screen, the screen resolution). In full screen with `renderer=d3d12` or `d3d11` and `[graphics] resolution=game`, the frame is drawn at it as it's set now (the game keeps laying itself out at the one it started with, its draws scaled to this) and stretched over the screen. `auto` is the resolution Windows has the display at, worked out at each start; `auto-75` three quarters of it each way (`auto-<percent>`, 1-100), `auto-50` half, `auto-taskbar` the display less the taskbar (its work area; windowed, the whole window fills it) |
| `resolution.ui` | `0037`, `0038` | `resolution.game` | The menu resolution: the interface is drawn at it and scaled to the window, so smaller is bigger. `auto` and `auto-<percent>` as `resolution.game` (`auto-75` on a 2560x1600 display is 1920x1200); `window` and `window-<percent>` that share of the game's window (`resolution.game`'s size: in the windowed modes its inside, the title bar and borders left out), fitted to `[ui] aspect`'s shape and made again as the window or the aspect changes |
| `resolution.background` | `0003`, `0004` | `2048x2048` | The 3D world's resolution; larger than the window is sharper and slower, `4096x4096` at most. `[graphics] background` sets it in its place (`renderer=d3d12` and `d3d11`) |

The resolutions take `auto` (the display's resolution as Windows has it: the main display's when the game starts, the window's display for the window's size) and `auto-<percent>` (that share of it each way). A key taken out goes back to its default.

**Frame pacing.** At 60 FPS the game counts each frame as a 60th of a second whatever it took (its tick, `GameManager::CheckTick` in XIClient's names, says 1), so when the frame rate drops, what it times by frames runs slow. `framepacing` gives the characters' motion (`AnimationTrack::UpdateFrame`'s step through a motion and `UpdateBlendState`'s blends and fades) the frame's real time instead, the last four frames averaged (1 within 4%, as the game smooths its own tick), up to 4. `framepacing.ui` runs the interface's root update and the chat's again for each whole 60th a long frame stood for beyond its one (up to 4 more), and takes the same off the chat windows' countdown to scrolling their new lines in. `framepacing.camera` runs the camera's three loops over the frame's 60ths twice a frame (once, its wall collision shows every other one of the two steps it settles in, and the camera flickers against a wall) and has its push out to the side go the whole way at once. Each acts only at 60 FPS (divisor 1); the game's own timing stands otherwise. VanaCore finds each in FFXiMain.dll by its code (`Frame pacing: the game's timing found ...` in the log) and patches it in or out as the settings change. This is the FrameFix plugin's work (rockerudon, MIT: `THIRD_PARTY_NOTICES.md`), done by VanaCore: FrameFix isn't loaded while any of the three is on (`/plugin load framefix` and boot.txt's say why) and is unloaded if it was, and loads again once all three are off. Its own 60 FPS setting is `fps.max`'s.

FFXI caps itself at 60 / divisor, a setting of its own (2, so 30 FPS, by default); 60 is its ceiling. VanaCore picks the divisor whose cap is the lowest at or above `fps.max`, and limits the rest of the way itself: 60 is divisor 1, 45 is divisor 1 held to 45 by VanaCore, 30 is the game's default, 25 is divisor 2 held to 25. On the first frame VanaCore finds the game's divisor setter (FFXiMain.dll's "FPS limit" function, by its code) and stands in for it: when the game asks for its normal 30 FPS it gets `fps.max`'s divisor instead, and anything else it asks for in special states (e.g. divisor 4, 15 FPS) stands. The log shows the choice (`FPS: fps.max=45: the game capped at 60 FPS (divisor 1), then limited by VanaCore`). The game's own cap only holds while Present waits for the display: with `renderer=d3d12` or `d3d9` and `vsync=0` (the default) it would draw as fast as the graphics card goes, taking all of it (the rest of the PC lags), so VanaCore holds it to the divisor's rate itself, on a high-resolution timer.

### Graphics
`[graphics] renderer=d3d12` gives the game VanaCore's own Direct3D 8, which draws with Direct3D 12 (`src/gfx`, ported from xi-on-mac). The game, VanaCore's overlay and addons, screenshots and Ashita plugins all draw through it unchanged. It needs Windows 10 or later and a Direct3D 12 graphics card (feature level 11_0, resource binding tier 2). Without them, or with `renderer=d3d8` (the default), the game uses Windows' own Direct3D 8, and everything below except `aspect` is off. The log says which (`Graphics: gfx: Direct3D 12 on <card>`, or `Graphics: Direct3D 12 didn't come up; the game uses its own Direct3D 8`). Under Wine or Proton (Linux, the Steam Deck), Direct3D 12 comes up but its shaders don't compile: Wine's `d3dcompiler_47` (vkd3d-shader's HLSL compiler) has no Shader Model 5.1 resource arrays, and every shader here reads its textures through them. Microsoft's own `d3dcompiler_47` in the prefix (`winetricks d3dcompiler_47`) compiles them, and Direct3D 12 then draws under Wine and Proton (reported working on GE-Proton 10 with Mesa RADV; set `renderer=d3d12` again, as the switch below was kept). Without it, Direct3D 11 draws the game in its place, as with `renderer=d3d11`, rather than leaving the window black (`Graphics: Direct3D 12's shaders don't compile here ...; Direct3D 11 draws the game in its place`, and /vana's Renderer line says so); what's Direct3D 12's alone, DLSS and its colour grade, is off. The switch is kept: VanaCore sets `renderer=d3d11` and `d3d12.unsupported=1` in vanacore.ini, so later starts go straight to Direct3D 11, and for that start draws "DirectX 12 can't run here: switched to DirectX 11" in amber at the top left, under the label, for 20 seconds. The launcher's Renderer (Accounts) shows vanacore.ini's `renderer` and leaves it be at Start Game, so it shows DirectX 11 too; choosing DirectX 12 there again (or in /vana) has the next start try Direct3D 12 again, and VanaCore takes `d3d12.unsupported` out whenever Direct3D 12 does draw. When the graphics card stops on Direct3D 12 (a driver timeout) and VanaCore closes the game, it sets `renderer=d3d11` in the settings file first, so the next start is Direct3D 11's; its message says so, as does the log (`Graphics: vanacore.ini set to renderer=d3d11: the next start is Direct3D 11's`), and choosing DirectX 12 again goes back. A timeout stops the card for every game on the PC: one of them shows the message, and the others close without it.

`renderer=d3d11` gives the game the same Direct3D 8 as `d3d12` (`d3d8.c`) on a Direct3D 11 back end (`src/gfx/gfx_d3d11.c`) instead: the interface features below (`[ui] aspect`, `resolution=window`, supersampling, texture packs, VanaCore's own interface in a layer of the window's size) work as they do on Direct3D 12, for graphics cards and drivers where Direct3D 12 runs badly or not at all. So do the scene effects, FXAA, the anisotropic world textures, the scene filter, per-pixel light and sharpening: the same passes from the same HLSL (`gfx_d3d12.c`'s, fitted to Direct3D 11's registers by `fx_source`). The sun's shadow casters differ only in how they're kept: Direct3D 11's rings move on when full, so each caster's uniforms are kept in memory too and written again when needed, and one whose vertices went through a ring that moved on before the scene was done is left out that frame (the flicker watch says so). The two back ends are in the one library; `gfx_dispatch.c` sends the front end's calls to the one chosen. The log says `gfx: Direct3D 11 (feature level 11_1) on <card>`. `VanaCore.GfxTest.exe d3d11` runs the back end's and the Direct3D 8 tests on it.

`renderer=d3d9` gives the game a Direct3D 8 that hands each call to Direct3D 9 (`src/core/d3d9.cpp`, the approach of crosire's d3d8to9, written afresh): the game draws itself as it does with its own Direct3D 8, with none of the Direct3D 12 additions below, but through Direct3D 9, so Direct3D 9 tools work on it. `d3d9.dll` is loaded by name, so one beside the game's executable (ReShade's, or DXVK's for Vulkan) is used before Windows' own; the log says which (`Direct3D 9: <path>\d3d9.dll, on <card>`). The game, VanaCore's overlay and addons, screenshots and Ashita plugins all still see Direct3D 8. Where Direct3D 9 differs it's translated: vertex shaders get Direct3D 9's vertex declarations and input declarations, the base vertex moves from SetIndices to the draw, sampler settings leave the texture stage states, ZBIAS becomes a depth bias, CopyRects becomes StretchRect, UpdateSurface or GetRenderTargetData, and state blocks carry the Direct3D 8 state Direct3D 9 doesn't keep. Without Direct3D 9 the game uses its own Direct3D 8 (`Graphics: Direct3D 9 didn't come up; the game uses its own Direct3D 8`). `VanaCore.GfxTest.exe` runs its Direct3D 8 tests on it too.

What it adds:
- **Scene effects** on the 3D scene: ambient occlusion, height fog in the zone's own fog colour (lit by the sun when you look toward it), god rays from the sun, bloom, a colour grade, contrast-adaptive sharpening of the finished frame, and less shimmer (the scene is made smaller through a mip chain instead of one sample per pixel, the world's solid textures are filtered trilinear and 16x anisotropic, and the sky's are left alone so its clouds don't flicker). `effects=0` turns them all off; `[graphics.effects]` tunes each one.
- **Sun shadows**: the scene drawn again from the sun into two 4096x4096 shadow maps, a sharp one reaching `sun_near` units past your character (so your own shadow is always in it, however far back the camera is) and a wider one out to `sun_distance` (with `sun_mid`, a third between them), with soft edges that widen the farther a shadow falls. Everything casts by default (buildings, trees, cliffs, characters), including the zone behind and beside the camera for 30 seconds after it was last in view (and for as long as you stay within 40 units of where you saw it), so a low sun still throws those shadows in. Each copy of a repeated object (a zone's trees of one kind, drawn from one model) is kept on its own, told apart by where it stands. Objects the game draws from buffers it rewrites (trees, which sway) are kept as copies for that as well, 48 MB at most. Anything kept whose place comes into plain view without the game drawing it (it moved, or another level of detail is drawn) is dropped. Characters aren't kept (they move). `sun_casters=1` keeps the casting to characters. They show by day, fade as the sun nears the horizon or goes behind cloud, and hold the last sun the game gave when no lit object is in view. The game lights each object with directional lights of its own, tens of degrees apart for some; the sun is the one the world's lit objects use most, counted over the last second or two (in the world, so turning the camera doesn't change it), and another takes over only once clearly ahead. Both are smoothed over frames (`temporal`) so they hold still as the camera moves, held to what each frame shows so a running character's shadow stays whole and leaves no trail. The two maps take about 128 MB of video memory.
- **Per-pixel lighting** (`light=1`): the sun and moon light characters and objects per pixel instead of per vertex, so highlights don't depend on where a model's vertices fall; torches and other point lights stay the game's (`light=2` does them per pixel too). While a new object's shaders build it's lit the game's way, so nothing blinks out.
- **Faster frames**: the game's per-frame 16x16 occlusion check is answered at once instead of waiting for the graphics card to finish the scene (7–8 ms a frame with a 4096 background; `probe=gpu` reads it for real). Render pipelines are built off the game's thread and kept in `cache\` for the next session.
- **The interface keeps its shape** (`[ui] aspect`, `game` by default: the shape of the game's resolution, `[ffxi] resolution.game`): in a wider window (21:9, 32:9) the interface is full height and centered, in a taller one (16:10 for a 16:9 game) full width and centered, instead of stretching; the 3D world still fills the window. The mouse follows: over the interface it lands where the game drew it, over the world where it is. It needs a menu resolution of that shape: `[ffxi] resolution.ui=window` (or `window-<percent>`) is fitted to it, or a size such as 1280x720 for 16:9, which with `[ui] native=1` is drawn at the window's resolution. /vana > Client > Game > **UI aspect ratio** sets it.
- **A cel-shaded look**, off unless asked for: ink lines around objects and along sharp folds (`outline`), brightness in a few flat steps with the colours kept (`bands`), and texture detail flattened into even patches with the edges kept sharp (`smooth`). VanaCore's own, on the same pass as the other effects; the interface isn't touched.
- **Depth of field**, off unless asked for (`dof`): your character stays sharp and the scenery behind blurs with distance. The focus follows the character (the nearest thing just below the middle of the screen, where FFXI's camera keeps them), eased so it doesn't jump when something passes; `dof_focus` fixes it instead.
- **Texture packs** (`textures=`): high-resolution replacements for the game's textures, made with xi-on-mac's `tools/make_texpack.py`.
- **Anti-aliasing** (`antialias=fxaa`): FXAA on the finished 3D scene, before the interface is drawn over it, so text stays sharp. It smooths the stair-steps along edges (a staircase becomes a slope) and specks a pixel wide, at the cost of a little softness. It runs with `effects=0` too.

`background` is the background resolution: FFXI draws its 3D scene into a picture of its own and puts that on the screen at the window's size, and every effect runs at the picture's size. With `renderer=d3d12` or `d3d11` it's VanaCore's, 3072x3072 unless set (`launcher`, the old value, is 3072x3072 too; the launcher's `[ffxi] resolution.background` doesn't come into it). `background=4096x4096` (512x512 to 8192x8192, or one number for a square) draws it at that size instead, while the game runs: the renderer makes the scene's picture that size itself (`Graphics: d3d8: the 3D scene drawn at 4096x4096 ([graphics] background)`), and `0003`/`0004` are served at it when the game starts (no side past 4096, the renderer drawing it larger). The game's own Direct3D 8 and `d3d9` have only `resolution.background`. Bigger is sharper and slower: 3072x3072 is about 2.5 times a 2560x1440 screen's pixels, 4096x4096 about 4.5. DLSS sets the size while it's on. /vana stats' hardware line and /vana > Client > About say the size the scene is drawn at. Multisampling the back buffer (Ashita's `presentparams.multisampletype`) can't smooth the scene: it would smooth only the interface, since the scene is drawn into that picture first.

`aspect` works with every renderer. It sets the 3D scene's shape, as the `aspect` addon does: the game draws the scene for its configured resolution, so in a window of another shape it's stretched. VanaCore finds the camera in FFXiMain.dll by its code (`Graphics: aspect ratio: the camera hangs from FFXiMain.dll+0x...` in the log).

A helper that ends or stops answering for half a second is let go; DLSS that isn't there (no RTX card, an old driver) puts the scene back at its own size. The motion is the camera's alone, exact for the scenery; for what it isn't (the game's effects, which are blended over the scene and can't say how they move; characters, plants and boats, which move on their own) DLSS gets a mask (its bias-current-colour mask: `[graphics.effects] dlss_reactive` for the effects, from the scene with and without them, `dlss_reactive_moving` for the moving things, drawn again into it) saying how far to lean on this frame there instead of its history, so they don't smear, double or freeze; `dlss_motion_all` (off; `dlss_motion` before, so an old 1 is dropped) guesses their motion instead, by matching draws to the frame before's. A full-screen game (`[ffxi] mode=fullscreen`) is shown in a borderless window covering its monitor, at the desktop's own resolution, with the frame drawn at it (`[graphics] resolution`).

### Window
`[ffxi]` `mode` and `resolution.game`, `[window]` and `[graphics] resolution` set the game window while it runs: save `vanacore.ini` and it changes within half a second (`Window: now borderless, 2560x1440 ([ffxi] mode)`). Taking the keys out puts back the game's own kind of window at its size. A `vanacore.ini` from before `[ffxi]` has `mode` and `resolution` in `[window]`: VanaCore moves them to `[ffxi]` and `[graphics]` when the game starts (`Settings: [window] mode=borderless moved to [ffxi] mode`), and takes out `size`, the window being `resolution.game`'s size.

| Key | Default | Effect |
|-----|---------|--------|
| `[ffxi] mode` | `borderless fullscreen`, or `[ffxi.registry] 0034` | FFXI's four: `fullscreen`, `windowed` (a frame and title bar), `borderless` (borderless windowed) or `borderless fullscreen` (borderless, covering its monitor; `windowed` again returns it to where it was). `0`–`3` work too, as `0034` numbers them. With `renderer=d3d12` or `d3d11`, `fullscreen` is `borderless fullscreen` (the `/vana` window offers only the latter); with `renderer=d3d8` or `d3d9` it's Windows' own exclusive full screen |
| `[ffxi] resolution.game` | the main display's resolution | The game's resolution (Game settings), and in `windowed` and `borderless` the window's inside, e.g. `2560x1440`, which changes at once (the game's own resolution at the next start). Not the window's size in the full-screen modes: the window is the monitor, and the frame is drawn at its size (or the game's, `[graphics] resolution=game`) |
| `resizable` | 0 | `1`: the window's edges can be dragged (and a windowed one maximized); the size they're dragged to is kept as `lastsize` for the next start |
| `lastsize` | none | Written by the game with `resizable=1`: the window's inside after its edges were last dragged (`1600x900`), shown in the `/vana` window's Resolution as "(resized)", in the windowed modes. The window starts that size, and an unset `resolution.ui` (Same as Resolution) lays the menus out at the window's inside while it's resized; the game's own resolution stays `resolution.game`'s, so maximized or full screen stays sharp. A Resolution picked takes it out |
| `[graphics] resolution` | `game` | With `renderer=d3d12` or `d3d11`: `window` draws the frame (the back buffer, and the menu with `[ui] native=1`) at the window's size, so it's sharp at any size; `game` draws it at the game's resolution (`[ffxi] resolution.game`) and stretches it (the game's own interface can look better so). VanaCore's own interface is at the window's resolution either way |
| `dpiaware` | 1 | The game draws at the display's own pixels, per monitor. Without it, on a scaled display (125%, 150%) Windows draws the game at the smaller size and stretches it, blurring it (and a 1920x1080 window on a 125% laptop is 2400x1350 of real pixels). With it a window is its size in real pixels, so it looks smaller than before: pick a larger `size`. Read when the game starts; the log says the display's scale |
| `mouse.scale` | 1 | The mouse given to the game in its own resolution when the window is another size (the game never asks the window's size, so it would take the window's pixels for its own); `0` passes it as it is |
| `keepawake` | 1 | The screen saver, the display's sleep and the lock screen that follows them are held off while the game runs, as they were with the game's own full screen (VanaCore tells Windows the game's thread needs the display, and answers no when Windows asks the window whether the screen saver may start); `0` leaves them to Windows. Applies while the game runs |
| `close.shutdown` | 1 | Closing the window (its X, Alt+F4, the taskbar's Close) with a character in the game runs `/shutdown`, the game's own way out, in place of ending the game with the character still in the world. The window mode is FFXI's setting `0034`, as the launcher writes it: 0 full screen, 1 windowed, 2 borderless windowed, 3 borderless full screen (the launcher's default). The game itself knows only 0 and 1: for 2 and 3 VanaCore gives it 1, a window, and makes that window borderless (`Game setting 0034 = 1 (window mode 3, borderless full screen: ...)`). `[ffxi] mode`, when set, decides it instead (unless `registry.override=1` and `[ffxi.registry] 0034` is set), and changes while the game runs. Full screen is Windows' own exclusive full screen with `renderer=d3d8` or `d3d9` (from the next start); with `renderer=d3d12`, which has no exclusive mode, it's borderless over the monitor. The borderless modes have no edge of any kind: no frame, no Windows 11 border or rounded corners.

Pressing the window's title bar or edges (to move or size it) doesn't reach the game, nor does the mouse over VanaCore's own windows (`/vana`, addons' boxes that ask for it): not in the window's messages, DirectInput, or the button states the game reads with `GetAsyncKeyState` and `GetKeyboardState`. The log says which of those the game uses (`Input: the game reads the mouse buttons with ...`).

The game keeps its own resolution throughout: its interface is laid out for `resolution.game` and `resolution.ui`, and scaled to the window. VanaCore's own interface (its label, FPS counter, addons' text and the `/vana` window) is drawn with `renderer=d3d12` into a layer at the window's resolution, laid over the frame at Present: sharp, and its size and shape kept, whatever size the frame is drawn at and whatever the window's shape. Plugins' objects stay in the game's pixels, as they place them. A screenshot with VanaCore's drawing gets the layer laid over it. For a window of another shape, `[graphics] aspect=auto` fits the 3D scene to it and `[ui] aspect` keeps the interface's shape. With `renderer=d3d8` or `d3d9`, the window's mode and size work only for a windowed game (`0034=1`; Windows' own Direct3D 8 owns a full-screen one), and the frame is stretched to the window. Reads of the back buffer (screenshots) come back at the game's resolution, averaged from what was drawn.

`build\obj\VanaCore.GfxTest\<Configuration>\VanaCore.GfxTest.exe` runs the renderer's offscreen tests (xi-on-mac's `gfx_test` and `d3d8_test`, 32-bit): drawing, every scene effect, and Direct3D 8 through its COM objects. Run it from the repository's root; it exits 0 when all pass.

### Window title and label
Once the game creates its Direct3D 8 device, VanaCore sets the window title to `FINAL FANTASY XI` (the game's own, which window switchers such as XI Focus take as "not logged in yet"; `[client] title.vanacore=1` makes it `VanaCore v<version>`), and while a character is in the world, to the character's name (looked at once a second: the player's party slot and entity agree), back to that at the character select (`Overlay: window title ...` in the log). As the game starts, `VanaCore v<version> - CatsEyeXI` slides into the top-left corner after VanaCore's logo (`addons\vanacore\vana\logo.png`, sized to the label's box), stays five seconds, and slides out (the version lives in `src/shared/vanacore/version.hpp`). The log confirms each step (`Direct3D 8 device created ...`, `Overlay: drawing ...`). While the picture waits on something being made, a toast slides down from the top edge of the screen, in the middle: a dark rounded panel with a title in bold (a 60th of the screen's height), under it what is being made right now, a count on the right and a progress bar along the bottom (`overlay.cpp` toast_draw). `Starting DLSS` (or `Starting DLSS 5`, `Starting FSR`) while the DLSS helper starts and DLSS is made for the scene's size - the scene is drawn small and stretched meanwhile - with its stage under it and the bar at it, of four (`Starting the DLSS helper`, `Loading NVIDIA's NGX`, `Making DLSS 5 and DLSS for 1280x720 -> 2560x1440`, `Waiting for the first frame back`; FSR 1 has no stages: the bar sweeps), `Starting frame generation` with its two (made for the frame's size, its first frames back), `Starting frame generation`, `Compiling shaders` while the effects' shaders compile, with the shader compiling named under it (`Ambient occlusion`, `God rays`, `Depth of field blur`: `gfx_wait_step`, the names in `gfx_d3d12.c` fx_words) and the bar at `12 of 43`, and `Preparing shadows` while a tenth or more of the shadow casters wait for their pipelines (turning shadows on the first time), the bar at the casters ready. It comes after 0.15 s (a quicker wait shows nothing) and stays at least 1.2 s, goes with F11's hidden interface, gives up after 30 seconds, and the log says what it showed and for how long (`Overlay: "Starting DLSS" shown, 2.4 s`).

### The VanaCore window: `/vana`
`/vana` opens VanaCore's own window in game (`/vana` again, or its **x**, closes it; `/vana <tab>` opens it at a tab). **Client > VanaCore**, Client's first sub-tab (`/vana vanacore` or `/vana about`), shows VanaCore's banner, its version, the renderer and graphics card, the frame rate, the screen's size and where `vanacore.ini` is, sets the window's own scale (**Window scale**, 75% to 200%, `[vana] scale`: a percent of the size it takes for the screen, which it still shrinks to fit a small one), then has VanaCore's own settings (the addon windows' font, its drawing in screenshots, the chat log's load lines, Discord, Recompile shaders). `/vana scale <size>` sets it from the chat, for a window too small to read (a 4K screen) or too big to reach the control: up to 10 is times the usual size (`/vana scale 2`, `1.5`, `2x`), more a percent (`150`, `150%`), 0.5 to 3; `/vana scale 1` (or `reset`) puts it back, and `/vana scale` alone says what it is. The tabs change `vanacore.ini`'s settings: **Client** (Game: `[ffxi]` mode and resolution, `[window]` resizable edges and where the window or which monitor, Max FPS (30, 45 or 60), V-Sync, always on top, the mouse scaled to the game, sharp on a scaled display; Display: the game drawn at the window's size or the game's, the 3D scene's and the interface's aspect ratio; Layers (`/vana layers`): every effect and picture setting as one chip, green while on and red while off, each the same switch as its panel's on Graphics or Effects, with All off, which remembers what was on (`[vana] layers.kept`), and Put back; FPS counter: the counter, its corner and padding, the text's size and outline (the VanaCore label's too); Developer: logging, and the MCP server. The input settings, `[input]`, are the launcher's: it writes them at each start, the only time they take effect), **Graphics** (renderer, with a red line under it while the one chosen isn't the one the game started with; effects, anti-aliasing, supersampling with the size each choice draws the 3D scene at; DLSS; the draw distance of the zone and of characters, and the distance fog; the lighting: shadows and what casts them, ambient occlusion and its quality, reflections, bounce light, height fog, bloom, god rays; texture filtering; one effect shown alone: Debug view, beside Preset in the title. Per-pixel lighting and smoothing over frames are `vanacore.ini`'s alone: `light`, `temporal`), **Effects** (the picture's look: colour grades, clarity, sharpening, smoothing, the cel look, depth of field, normal maps), **Interface** (the game's windows, the chat: its lines, saving its log, its window, timestamps; menus, nameplates; the Config windows' sliders, which `[client] sliders.style=flat` draws as VanaCore's own: a plain bar, its fill up to the value, a knob and the ends, each in a colour and size of its own, `sliders.*` in `vanacore.example.ini`), **Options** (the camera's zoom and turning, NPC effects, zone lines), **Pivot** (`[pivot] enabled` stays in the ini, and `log` is under Client > Developer > Logging; every overlay in the pivot folder, found as the first folder down from it with a `ROM` folder or `FTABLE.DAT` in it, so `ffxi-mapsB4x1024` and `ffxi-maps8x2048` each show. Those in `[pivot.order]` are listed in its order, with arrows to move one up or down and a switch that takes it out, the rest keeping their order; the others are in an Off panel under them, with a switch that puts one in, last. **Refresh** looks at the folder again, for a new overlay), **Addons** (two pages: **List**, to load and unload them, and **Layout**, where their windows are and their scale; see ImGui below) and **Plugins**; `/vana` with a tab's old name (`lighting`, `shadows`, `window`, `input`, `image`, `style`, `options`, `chat`, `nameplates`, `trusts`, `camera`) opens the tab it's in now. A panel can hold sub-panels, each under a line with its title (DLSS 5, Logging, AI MCP, the chat's window and timestamps). Each panel's heading has a minus before its title that folds the panel shut (a plus opens it again; folded panels stay folded from one start to the next, in `config\addons\vana\settings.lua`), and each effect's heading has its own toggle (`[graphics.effects] <key>.enabled=0` turns it off and keeps its strength; turning on one whose strength is 0, as the cel look and depth of field are by default, sets one). The effects need VanaCore's own Direct3D 8: until the game starts with `renderer=d3d12` or `d3d11`, each shows off, greyed, and its toggle doesn't move. A tab taller than the window scrolls, by the wheel or its scroll bar. A toggle switches on a click; a choice goes to its next value on a click, the previous one with a click on its left arrow or a right click; a slider follows the mouse while held, and the wheel nudges it a step (in a tab that scrolls, the wheel scrolls it). Every change is written to `vanacore.ini` at once: the graphics settings apply straight away, the client ones within half a second, and those marked `*` the next time the game starts. **Reset to defaults** removes the tab's keys (the Graphics tab keeps the renderer). Drag the title bar to move the window; it opens where it was left (`[vana] x`, `y`). The mouse's buttons and wheel over it don't reach the game, nor a drag that started on it (FFXI reads them through DirectInput, which VanaCore blanks for it), so dragging a slider doesn't turn the camera; the cursor still moves.

Since 2026-10-15 the window is drawn the new way: the tabs above are pages in a list down the left (grouped under VanaCore, Settings and System, with a search box over them that finds a setting on any page), each page's settings in sections a line each, every section folding and resetting on its own; **Presets** (named sets of settings in `vanacore.presets.ini`, Export as a string or .json, Import) and **Experimental** (Mass Grass, the water shader, glow effects lighting) are pages of their own, and the Addons and Plugins pages open an addon's description, README and details beside the window (`/vana help <addon>`). It opens in the middle of the screen at first. The old window, as described above, is gone.

It's a VanaCore addon, `addons\vanacore\vana\vana.lua`, loaded when the game starts (before `scripts\boot.txt`), drawn with ImGui (`vana.imgui`'s draw lists, `draw.lua`), with its settings, their rows and the write path through `vana.config.set` in `data.lua` (a new setting is a row there), the Addons and Plugins list and addons' help in `addons.lua`, and presets' strings in `share.lua`. VanaCore's own drawing, its addons' and its plugins' aren't squeezed with the game's interface under `[ui] aspect`, so what they draw is where the mouse finds it.

### Commands
VanaCore answers some commands itself, before any plugin or addon sees the line: `/screenshot`, `/copy`, `/paste`, `/cancel`, `/freecam`, `/freelook`, `/fillmode`, `/exit`, `/terminate`, `/execstr`, `/sleep`, `/pause`, `/abtest`, `/camtrace`, and the /vana window's `/hud`, `/gamepad`, `/gamepads`, `/addons`, `/plugins` and `/pivot`. **Client > Commands** (`/vana commands`) lists them with what each does, and switches each off for a player whose own addon or plugin has a command of that name: VanaCore then leaves `/name` and `//name` to the plugins, the addons and the game, typed or from a script, a bind or a macro (`src/core/commands.cpp`; the window's own in `vana.lua`). `/addon`, `/plugin`, `/exec`, `/vana`, `/wait`, `/bind`, `/unbind`, `/unbindall`, `/alias` and `/raw` are listed too and stay on. `/alias` gives a command another name (`/alias /ss /screenshot`). The game's Config > HUD runs `/vana hud manager`, which stays with `/hud` off.
```ini
[commands]
copy=0              ; <name>=0 switches that command off (default 1 for each)
```

### Addons
How to write one, and the whole addon API, is in [docs/addons/README.md](addons/README.md).

VanaCore runs Lua addons of three kinds, all with the same commands. In game, type into the chat box:
```
/addon load <name>            several at once work too: /addon load example-hello aspect DistancePlus
/addon load <name> windower   from one kind's folder only (vanacore, ashita or windower)
/addon unload <name>
/addon reload <name>          from the folder it came from (or add a kind to switch)
/addon list
/addon info <name>            its file, version, author, description, link, memory and state
/addon link <name>            opens its addon.link (a web address) in the browser
/addon exec <name> <lua>      runs the Lua in the addon (what it prints goes to the chat log)
/addon kill <name>            unloads it without running its unload event
/addon unloadall              unloads every Ashita and Windower addon (VanaCore's own stay)
/addon silent [0|1]           no chat line as addons load and unload ([addons] silent)
```
`/addon ...` works the same. VanaCore answers in the chat log, naming the kind: `(Windower Addon) Loaded: DistancePlus 1.3.0.11 by Sammeh`, `(Ashita Addon) Loaded: aspect 1.0 by atom0s`, `(VanaCore Addon) Loaded: hello 1.0 by CatsEyeXI`.

Addons live in a folder per kind under `addons\` next to `VanaCore.exe`, each as `<name>\<name>.lua`. `/addon load <name>` looks in them in this order, so when two have an addon of the same name, VanaCore's comes first, then Ashita's, then Windower's; name the kind to load another. One addon of a name is loaded at a time.

| Folder | For | Libraries |
|--------|-----|-----------|
| `addons\vanacore\` | VanaCore's own addons | `addons\vanacore\libs` |
| `addons\ashita\` | Ashita addons | VanaCore's copies of Ashita's (`common`, `sugar`, `switch`, `chat`, `settings`, ...): `addons\vanacore\libs\ashita-4.30` (Ashita 4.30's, with ImGui 1.81's names defined over them for addons written for 4.16; `-4.16` with `[addons] ashita.libs=4.16`), then `addons\vanacore\libs\ashita`, shared by both |
| `addons\windower\` | Windower addons, laid out as Windower's own addons folder | `addons\windower\libs` (Windower's libraries), `addons\windower\res` (its resources); what they don't have comes from VanaCore's copy of Windower's, `addons\vanacore\libs\windower\libs` and `res`, so an addon copied in alone (GearSwap) runs |

Which kind an addon is comes from its main file: `vana.*` is VanaCore's own; otherwise `windower.*` and `_addon.*` against `ashita.*`, `AshitaCore` and `addon.*`, whichever it uses most; its folder's kind when it uses none of them. Each addon runs in its own LuaJIT 2.1 state (Lua 5.1, plus LuaJIT's `ffi`, `bit` and `jit`), with only its kind's API and libraries: `require` looks in the addon's folder, then in its kind's libraries. VanaCore's own addons are in the repository's `addons/vanacore/`: Two load at start without a `boot.txt` line: `vana`, the `/vana` window (`[addons] vana=0` switches it off), and `keybinds`, the key binds window, which is always on (`/addon unload keybinds` leaves it loaded, `reload` works, and the `/vana` Addons tab shows it without a switch). Every other one, `freecam` and `loadscreen` too, loads from `scripts\boot.txt` like any addon, so the launcher's Addons page, the `/vana` Addons tab (and the Loading Screen page's switch), `/addon load` and `unload`, and editing the file all switch it the same way. The default `boot.txt` loads `freecam` and `loadscreen`, so a new install has them on; until 0.8.276 they loaded by themselves, and an existing install's `boot.txt` doesn't get their lines, so there they're off until switched on. A VanaCore addon added later is off until switched on too. With `delay.login` they load at login, so the loading screen first shows at the first zone change. The loading screen's settings are `/vana` > Options > Loading Screen (`/loadscreen` opens it; `[loadscreen]`): its switch; which parts show (where from, the bar, what it's doing, the file, and a line at the top counting the people still loading, off by default); Data Display: Widget scale, Position (X and Y), the progress bar's colour, a panel behind it all (Panel background colour, Panel opacity) and Single line zone info (From → To on one line); Screenshots Display: a random screenshot from `screenshots\` behind it with its edges darkened (Edge shadow), fading in and out at its own pace (Fade in, Fade out). Preview shows it as a load would. A logout or `/shutdown` (the server's zone-out says which) shows none of it: the game fades to black, with no screenshot or text, and the black lifts as the title screen's windows open (10 s at most); `/loadscreen preview logout` shows that fade. `hello` shows a box that says hello world, and `/hello <text>` changes it.

**sendkey** (`addons/vanacore/sendkey`, `/addon load sendkey`, or a line in `scripts\boot.txt`) binds a controller button or a key to a key that Windows sends to every program, not only the game: for what listens to the keyboard on its own but can't see the controller (Discord's push to talk, OBS, a macro tool). The key goes down as the button does and up as it's let go, so holding the button holds the key; it never reaches the game itself. It sends with `SendInput` from the game's process, so it works whatever rights Discord runs with, on VanaCore's renderers alike.

```
/sendkey bind <from> <to> [block]   /sendkey bind pad:rb f13        R1 (RB) holds F13
                                    /sendkey bind f9 ctrl+shift+m    F9 sends Ctrl+Shift+M
/sendkey learn <to> [block]         then press the button or key to bind
/sendkey unbind <from> | list | clear | names
/sendkey test <to>                  sends the key for half a second, to try what listens for it
```

`<from>` is `pad:<button>` (XInput: `a b x y lb rb lt rt start back ls rs up down left right`, and PlayStation names: `cross circle square triangle l1 r1 l2 r2 l3 r3 options share`), `joy:<n>` (a DirectInput controller's button n, from 0, for pads that aren't XInput ones), or a keyboard key with `ctrl+` `shift+` `alt+` held (`f9`, `ctrl+f9`). `<to>` is a key with any modifiers (`f13`, `ctrl+shift+m`, `volumemute`; `/sendkey names` lists them). There are no default binds. Without `block` the button or key still does its usual job in the game; with it the game doesn't see it. Choose a `<to>` the game doesn't use (F13 to F24 are good: most keyboards have none); the keys it sends are kept from the game for a moment as they come back through its window. Binds are saved in `config\addons\sendkey\binds.txt` and come back with the addon. Controllers only report while the game is in front, unless `[input] gamepad.allowbackground=1`; in Discord, bind Push to Talk to the key it sends.

Ashita addons see Ashita interface 4.16 (CatsEyeXI's Ashita) unless `[addons] ashita.interface=4.30` says 4.30. Addons check it to choose their code, so 4.30 gives each Ashita addon what Ashita 4.30's Addons plugin does: `ashita.interface_version` 4.3 and `ashita.addons_version` 4.1 (4.16's are 4.16 and 2.1), the Addons plugin's `GetInterfaceVersion()` 4.30, ImGui text as it's given (4.16's Addons read `%%` as `%`), the SDK methods 4.30 added (`IEntity:GetMogMotionId`, `IParty:GetMemberMasterLevel`, ...), and 4.30's other additions: `ashita.memory.assembler` (x86 assembly, assembled by AsmJit and read by AsmTK as Ashita's is), the `AddonManager` global (the Ashita addons loaded and their details) and `find`/`get_base`/`get_size`'s `':ffximain'` and `':boot'`. Both have `addon.instance` (`state`, `current_frame`, `get_memory_usage()`). The libraries are Ashita 4.30's either way (`addons\vanacore\libs\ashita-4.30`, then `addons\vanacore\libs\ashita` for what both versions share): they have everything 4.16's had and 4.30's additions (`chat.color`, `reflex`, `ffxi\targets`, ...), and the ImGui 1.81 names 1.92 renamed or dropped (`ImGuiCol_TabActive`, `ImDrawCornerFlags_All`, ...) are defined over them as ImGui 1.92 itself keeps them, so an addon written for either version finds what it asks for and no addon needs the switch for its libraries. `[addons] ashita.libs=4.16` gives addons 4.16's own libraries instead (`addons\vanacore\libs\ashita-4.16`). ImGui is 1.92 either way, taking 1.81's numbers from an addon that loaded 4.16's `imgui` library. Plugins aren't affected: each says which interface it's built for, and VanaCore hosts both. Both settings apply to an addon as it loads (`/addon reload`).

**Scripts.** `scripts\boot.txt` next to `VanaCore.exe` runs when the game starts (on its first frame, at the title screen), except that its addons wait for a character to log in (`[addons] delay.login`, below), for the addons and plugins to load every time. Each line runs as if typed into the chat box; lines starting with `#` are comments, and `/wait <seconds>` delays the lines after it:
```
# scripts\boot.txt
/addon load aspect
/addon load distanceplus
/wait 2
/addon load tparty windower
```
With `[addons] delay.login=1` (the default; the **Startup** switch on the `/vana` Addons tab), `boot.txt`'s `/plugin` lines run as the game starts, as they do on Ashita, and the rest of it (its addons) doesn't run at the title screen but once a character is in the world (the player's party slot and entity agree, looked at four times a second): `Addons: <character> is in; running the rest of scripts\boot.txt` in the log. Plugins aren't held because some patch the client, and the client reads the character's inventory, and its sort-order caches (`USER\<id>\is.dat` and the others), at login: CatsEyeXI's cexidats and cexislots patched after that left custom items in the caches again at every login, a row more each time in the Items menu. The rest runs once per game start, so logging out and in again doesn't load everything twice, and `/wait` counts from the login. What loads late doesn't see that login's packets, but for one: each Ashita addon it loads gets the login's zone-in (0x00A) once as it loads, as on Ashita, where it would have loaded at the title screen and seen it (logincmd runs the character's profile from it): `Addons: <addon> loaded after the login ([addons] delay.login): it gets the login's zone-in packet (0x00A) now` in the log. It comes as the game got it, not injected, and blocking or changing it does nothing; after a zone-out (0x00B) it doesn't come, as the next zone-in will. The login's other packets don't come again, so an addon that needs them reads the game's state itself. `delay.login=0` runs all of it as the game starts. `/vana` and `keybinds` are loaded either way, and `/addon load` typed by hand isn't held. CatsEyeXI's required extensions, the plugins cexidats and cexislots and the addon customcolors, load first whatever order `boot.txt` has them in (each at its pass, before any `/wait`), and load even when `boot.txt` doesn't name them, as long as their files are there (the log says so); `/plugin unload` and `/addon unload` leave them alone (`reload` works), and the `/vana` Addons tab lists them first without a switch.

`/exec <script>` runs `scripts\<script>.txt` the same way (`/exec boot` runs the boot script by hand). Lines that aren't VanaCore's commands go to the game's command line (and addons' command events), so `/echo`-style game commands work too once the game's command line is hooked.

**Addon settings.** `vana.settings` keeps each addon's files under VanaCore's folder, keyed on the addon's name as its folder spells it:

```
settings\addons\<Addon>\settings.json               scope 'global': the same for every character
settings\addons\<Addon>\<Character>\settings.json  scope 'character': the character logged in
settings\plugins\<Plugin>\                         plugins' own, laid out the same (nothing writes there yet)
```

```lua
local store = vana.settings.register({ scope = 'character', defaults = { favorites = {}, opacity = 0.8 } })
store.data.favorites[230] = 'Ru\'Lude Gardens'
store:save()
```

A store's file is made from its defaults when it isn't there, so it's there to read and edit. A per-character store holds its defaults until a character is in (looked for twice a second, as the game's own party slot and entity agree), then reads that character's file; another character or a logout saves what changed first. What changed in a store is also saved after the addon's own `unload` handlers, so a setting changed without `save()` isn't lost; a store that didn't change isn't written, so a file edited by hand while the game runs stays as it is until `store:reload()` (or the addon's next load) reads it. A file that isn't JSON is kept beside it as `settings.json.broken`, the player is told, and the defaults are used. The full guide, with the API, JSON rules and moving from Ashita's settings library, is `docs/addons/08-settings-and-files.md`. `src/core/lua/settings.lua`, tested by `tools/luatest/settings_test.lua`.

An error in an addon goes to the chat log (its first line, once while it repeats) and to the log with its stack traceback. An addon whose file or `load` event fails isn't loaded; one that keeps erroring for 5 seconds (usually on every frame) is unloaded, while a shorter burst is left alone. An addon that crashes (an access violation in its `ffi` code, say) is unloaded and its Lua state abandoned, and the game carries on.

**Ashita addons** run through `src/core/lua/compat/ashita.lua`, which puts Ashita v4's API over `vana`: its `load`, `unload`, `command`, `d3d_present` (and `d3d_beginscene`/`d3d_endscene`, at the same Present), `mouse`, `key`, `key_state`, `key_data`, `xinput_button`, `dinput_button`, `xinput_state`, `packet_in`, `packet_out`, `text_in`, `text_out` and `plugin_event` events (their tables, `blocked`, a packet's `data_modified` or `data_modified_raw` changed in place); memory, fs (the whole namespace: `rename`, `normalize`, `status`, ...), tasks, time, misc, regex and bits functions; `ashita.addons_version` (2.1: before 2.2 the printf-style ImGui calls took a format string, as VanaCore's do) and no `ashita.interface_version`, as the interface 4.16 Addons plugin has it, so addons take their Ashita 4.16 paths (ImGui 1.81, item icons by `ImageSize`) rather than 4.3's; the configuration manager (its `boot` settings read from `vanacore.ini`; `ffxi.registry` is the game's settings as VanaCore hands them to it, `[ffxi]`'s or `[ffxi.registry]`'s); the chat manager's `QueueCommand`, `AddChatMessage` and `Write`; the memory manager's party, entity, target and player getters (`GetMemberName`, `GetDistance`, `GetTargetIndex`, `GetMainJob`, `GetLoginStatus`, ...); the GUI manager, which their `imgui` library draws with (see ImGui below); the plugin manager's `Get('addons')` (interface 4.16) and `RaiseEvent` (plugins' `HandleEvent`, addons' `plugin_event`); and `GetPlayerEntity()` / `GetEntity(index)`, views over the game's own entity structures (Ashita's `entity_t`: every field reads live, `Name` as a string, and a write reaches the game, so ceximodels' and sexchange's `ModelUpdateFlags` and `Look` changes show). LuaSocket's C half (`socket.core`, `mime.core`) is built in for every addon, so both kinds' `socket`, `mime` and `socket.http` work (GearSwap, Overlay, frenslist); LuaSec's `ssl` isn't. Primitives' textures are drawn. Once logged in, the settings library keeps each character's settings in `config\addons\<addon>\<name>_<id>\`. Tested: `aspect`, `xicamera`, and 15 more of the CatsEyeXI client's addons load.

On the Ashita layer's objects a name neither Ashita's API nor VanaCore has reads nil, as it does on Ashita's own (addons feature-test methods and read fields that were never there: XIUI's `player.isZoning`), and the log names it once with the line that read it. The log also notes events an addon listens for that VanaCore doesn't raise yet (`incoming chunk`, `packet_in`, `text_in`, `mouse`, …).

How it hooks in: on the first frame VanaCore finds FFXI's command line (FFXiMain.dll+0x80BD0, the function every typed line, macro and menu command goes through) and its chat log writer (FFXiMain.dll+0x765D0) by their code, and logs where (`Chat: command line hooked at ...`). Lines VanaCore or an addon handles never reach the game; an unknown `//` command gets an error rather than going out as chat. The game data comes from the entity list (FFXiMain.dll+0x47E980), the party (+0x62EE38), the player (+0x4834C8) and the target window (through +0x5765EC), found by their code the first time an addon asks (`Game data: ...` in the log). Addons are not yet unloaded when the game closes, so an addon that saves only in its `unload` event doesn't save then (`xicamera` saves on every change).

### Plugins
VanaCore runs native plugins too, with commands like the addons':
```
/plugin load <name>            plugins\ashita\<name>.dll (or plugins\windower\), the first that has it
//<name> args                   a Windower plugin's command (//ffxidb, //st)
/plugin load <name> windower   from one kind's folder only (ashita or windower)
/plugin unload <name>
/plugin reload <name>
/plugin list
```
`//plugin ...` works the same, and so do the lines in `scripts\boot.txt` (`/plugin load findall`). Answers name the kind: `(Ashita Plugin) Loaded: FindAll 1.16 by Thorny`. Plugins live in `plugins\ashita\` and `plugins\windower\` next to `VanaCore.exe` (VanaCore makes both folders); when both have a plugin of the same name, Ashita's is loaded unless the command names the kind.

**Ashita plugins** (Ashita v4's `plugins\*.dll`, built against its SDK at interface version **4.16** or **4.30**) run as they do in Ashita: VanaCore loads the DLL, reads the interface version it was built for (`expGetInterfaceVersion`), and hands it VanaCore's own implementation of that version's `IAshitaCore` and managers. The two versions lay their objects out differently (4.30 adds and removes methods in the entity, party, player and target objects, changes key binds and packet queueing, and wraps a newer ImGui), so VanaCore has both, built from the SDK's headers by `tools/gen_ashita_abi.py` into `src/core/compat/ashita/abi.hpp`; `tools/gen_ashita_abi.py --test` makes a test plugin, built against the SDK itself, that calls every one of the 1,275 (4.16) and 1,328 (4.30) methods and checks each lands in the right place with the stack intact. A plugin's `GetInstallPath()` is VanaCore's folder, so plugins keep their files where Ashita keeps them: `config\plugins\<name>\`, `resources\<name>\`. Plugins run in priority order (as Ashita does), before addons: they see every command line (`HandleCommand`; those with priority 0 or more after the addons, where Ashita's Addons plugin sits), each frame (`Direct3DInitialize`, `Direct3DPresent`), every packet the game receives or sends (`HandleIncomingPacket`/`HandleOutgoingPacket`, which can change or block it), and each other's events (`RaiseEvent`/`HandleEvent`). A plugin that crashes in a call is disabled and its DLL left loaded, and the game carries on.

What they get:

| Memory manager | The game's own structures, in the SDK's layouts: every entity (`IEntity`: all 268/270 getters and setters), the party and alliance with status icons (`IParty`), the player (`IPlayer`: stats, skills, job points, buffs, recasts, key items, known spells, job levels through the game's own functions), the target (`ITarget`), the inventory (`IInventory`: containers, treasure pool, equipment, check info), auto-follow, the cast bar |
| Resource manager | Items (`GetItemById`, `GetItemByName`: all 23,771 in the client's item DATs, names, log names and descriptions in English and Japanese, the header numbers and icon, read from the DATs the first time a plugin asks, in both the legacy 0xC00-byte and the September 2026 retail 0x1400-byte record formats), string tables (`GetString`: key items, jobs, zones, titles, ... — every table in Ashita's DAT map, by index or by text), DAT paths by file id (`GetFilePath`), entities by index and id |

Status icons come from the game's DAT (Ashita's status_icons, `ROM\119\57.DAT`: the description, whether it can be cancelled or its timer is hidden, and the icon as a BMP), the recasts (`IRecast`) and the target window (`GetRawStructureWindow` and its getters) from where the game keeps them, and `QueueOutgoingPacket` puts a packet in the game's own outgoing queue, as Ashita does. A plugin that takes a macro's line and queues it again as a typed `/raw` line (Shorthand does it for every `/ma`, `/ws`, `/ja`, `/item`, `/ra`, `/attack` and `/target`) has that copy run at once, in the line's place and as a macro line: the macro waits at an `<st>` line for the cursor as it does without the plugin, and pressing it again with the cursor up is ignored instead of printing "You cannot perform that action on the selected sub-target." (`src/core/chat_raw.h`). Textured primitives are drawn: a texture from a file, memory, a module's resource or the plugin's own, stretched over the primitive and tinted by its colour, its offset moving it; primitives' borders too. Text handlers (`HandleIncomingText`, `HandleOutgoingText`, for plugins with `UseText`) get every line coming into the chat log and every line going to the game that no command took, as Ashita has them: the original, a 4096-byte buffer for a change (empty until one is made), the mode and indent to change, whether it's VanaCore's own, and whether one before blocked it. Keyboard and mouse callbacks work: a plugin's `IKeyboard::AddCallback` gets the game's DirectInput keyboard reads (`GetDeviceState`, and `GetDeviceData` with room for more events: how Thirdparty holds down the keys other programs send through Windower's keyboard MMF) and each key's window message (the virtual key and its flags, as a keyboard hook has them; one it blocks is kept from the game's DirectInput keyboard too, until it's let go), and `IMouse::AddCallback` each mouse message over the game window, in the game's pixels (Minimap's drag and zoom; a left press only with Shift held, so a plugin's window moves with Shift + left drag and a plain click stays the game's); each is called as its plugin, and goes when it unloads. Controller callbacks work too: `IController::AddCallback` gets each DirectInput controller read (`GetDeviceState`, `GetDeviceData`) and each change of a button, axis or hat (by its offset in `DIJOYSTATE`), and `IXInput::AddCallback` each `XInputGetState` and each change of a button, trigger or stick (Ashita's numbers: 0-15 the buttons, 16 and 17 the triggers, 18-21 the sticks). A change one blocks is kept from the game until the control changes again, one it changes reaches the game changed, and `QueueButtonData` sets a control as if from the controller; movement inside the dead zone raises nothing unless `SetTrackDeadZone(true)`. Abilities and spells come from the game's own DAT (Ashita's spdata, `ROM\118\114.DAT`: its records unscrambled as POLUtils does), named from the `abilities.*` and `spells.*` string tables (Shorthand). Each of the rest, when a plugin calls it, does nothing and returns zero, and the log names it once (`Ashita plugins: <plugin> called <method>, which VanaCore doesn't implement yet`). Two plugins are refused with the reason: `Addons` (Ashita's own Lua addon host; VanaCore runs Ashita addons itself) and `Sequencer` (it finds what to patch by reading Ashita's own packet code).

**Windower plugins** (Windower 4's `plugins\*.dll`, interface `0x04070300`) get VanaCore's implementation of what Windower's `Hook.dll` gives them: the plugin manager and its settings, the console, text objects, primitives, the packet stream and the chat log. Windower never published that interface; VanaCore's declarations (`src/core/compat/windower/abi.hpp`) come from Hook.dll's own classes (their slots, and what each reads and writes) and from how LuaCore.dll and the plugins call them. **Windower 3 plugins** (interface `0x0004xxxx`, such as StatusTimer; Windower 4 itself refuses these as "out of date") run on a Windower 3 host with what StatusTimer uses of it; a call to any other part does nothing and the log names it once (`Windower plugins: <plugin> called Windower 3's <object> slot <n>, which VanaCore doesn't know`).

Plugins see VanaCore's folder as Windower's. Windower keeps its plugins' files next to them in `<Windower>\plugins\`: `settings\`, `resources\` (spells, abilities, items, statuses, areas) and a folder per plugin (`FFXIDB\`). So a Windower plugin's file access under VanaCore's `plugins\` goes to `plugins\windower\` instead (`plugins\windower\settings\FFXIDB.xml`, `plugins\windower\FFXIDB\map\`): copy those folders from Windower's `plugins\` into `plugins\windower\`. The log names the first redirections (`Windower plugins: ...\plugins\settings\FFXIDB.xml is ...\plugins\windower\settings\FFXIDB.xml`).

What they get: `//<name> args` goes to the plugin (`<name>` is its DLL's name, or a Windower 3 plugin's own: `//st`), and a `//` command nothing else knows to their `UnhandledCommand`. Each frame, inside the frame's scene as in Windower, they get `PreRender` (Windower 3: their frame call; FFXIDB draws its minimap on the device there); then VanaCore draws their text and primitives in the order they were made (text in UTF-8 with Windower's `\cs(r,g,b)` colours, fonts in points; primitives filled, or an image from a PNG, BMP or JPEG file or the plugin's own resources, tinted and tiled), then `PostRender`. Every packet the game receives or sends goes past `IncomingChunk`/`OutgoingChunk`, which can change or block it; plugins can add packets and read the last one of each id. Console lines and `AddToChat` go to the chat log (a console line's `\cs(r,g,b)` becomes the nearest chat log colour). The mouse over the game window goes to their `Mouse` as Windower gives it (type, where in screen pixels, the wheel's turn): a plugin that takes it keeps it from the game, which is how FFXIDB's minimap is dragged and zoomed (the wheel; Ctrl + wheel scales it). A left press reaches them only with Shift held, so plugins' windows move with Shift + left drag and a plain click stays the game's (their releases always come); what a plugin or addon takes (a press, a wheel turn) is kept from the game's DirectInput mouse too, so turning the wheel over FFXIDB's minimap zooms the map, not the camera, and dragging it doesn't turn the camera; the wheel comes in notches (its turn / 120), as Windower hands it them. A C++ exception a plugin throws and doesn't catch (FFXIDB on `//ffxidb pos o 1`) is reported in the chat log with its message and the plugin carries on; only a crash (an access violation and the like) disables it. And the game itself: Windower plugins read it through a table of 14 pointers into the state Windower keeps from the server's packets (logged in and the zone; the server's clock; the player's id, index, name, jobs, HP, MP and buffs; merits, key items, all 32 bags of items, the treasure pool, equipment, job points, missions). VanaCore keeps the same block, laid out as Windower's, from every buffer the game receives from the start (`src/core/compat/windower/state.cpp`: Windower's handling of 22 incoming packets), whether a Windower plugin is loaded or not.

Not yet: chat text callbacks (`IncomingText`/`OutgoingText`), the item callbacks (`AddItem`/`RemoveItem`), and Windower's timing of three buffs (the words at player + 0x136). `Keyboard` gets each key's press and release (its DirectInput code, and 1 down or 0 up: what Windower addons' `keyboard` event has; the plugins seen so far ignore them), and returning true keeps it from the game.

Tested in a test process with the real FFXiMain.dll, the received packets fed through the game's hooked decryption: a test plugin built on VanaCore's declarations (settings, console, text with `\cs` colours and extents, primitives filled, textured, fitted and tiled, files written under `plugins\settings\` landing in `plugins\windower\settings\`, commands, `SendCommand`, `UnhandledCommand`, packets seen, changed, blocked and added, the game state from 0x00A, 0x063, 0x020 and 0x055, reload); `FFXIDB` 1.2.3.14 loads, reads its settings and map data from `plugins\windower\`, answers `//ffxidb`, sees zoning in and unloads cleanly (its minimap draws round the player, whom it finds in the game's memory once logged in: to try in game); `StatusTimer` loads, reads `StatusData.txt` and Windower 4's resources, draws its timers for the player's buffs, answers `//st` and unloads cleanly.

How it hooks in: packets through the game's own decryption of each buffer it receives (FFXiMain.dll+0xDD410) and encryption of each it sends (+0xDD2E0), where Ashita hooks them too, found by their code on the first frame (`Packets: hooked ...` in the log); VanaCore rebuilds a buffer only when a plugin handles packets or has added one. The inventory is the game's character object (the global at FFXiMain.dll+0x4DDC28) + 0x9860; key items are the game's 4,096-bit table (the CatsEyeXI client's; retail's is smaller, which Ashita's own pattern expects).

### ImGui
Ashita's plugins and addons draw their windows with Dear ImGui, and VanaCore has it built in: `third_party/imgui`, 1.81 WIP at commit 6487860a, the version Ashita 4.16 builds in (the SDK's copies of its structures match it field for field: 291 sizes and offsets compared). One ImGui draws for all of them, each frame after plugins' fonts and primitives and under VanaCore's own window (`/vana`). It works in the game's pixels, as Ashita's does, like addons' fonts, primitives and mouse events, so an addon's windows line up with what it draws itself at any game resolution; its drawing is scaled onto VanaCore's interface, so with `[ui] aspect` it stays where the mouse finds it, and VanaCore's own ImGui windows are scaled to keep their size.
- **Plugins** (interface 4.16): `IGuiManager`'s 371 methods, each ImGui's own (`src/core/compat/ashita/gui.cpp`, the forwarders generated from the SDK by `tools/gen_ashita_gui.py`). A plugin can't destroy the context everything draws with, or swap ImGui's allocators (the log says so). Plugins built for 4.30 wrap ImGui 1.92, which VanaCore doesn't have: their windows don't show.
- **Addons**: their `imgui` library (Ashita's `addons\ashita\libs\imgui.lua`, as it is) finds ImGui as `AshitaCore:GetGuiManager()`, which is `vana.imgui` (`src/core/lua_imgui.cpp`), with Ashita's Lua conventions: a pointer is a table (`imgui.Checkbox('x', t)` toggles `t[1]`; an array is `t[1]`..`t[N]`), and a `p_open` that isn't a table is none; ImVec2 and ImVec4 go in as `{x, y}` and come back as numbers (`local x, y = imgui.GetWindowPos()`); `GetIO()`, `GetStyle()`, `GetFont()` and `TableGetSortSpecs()` are live objects (`io.DisplaySize.x`, `style.Colors[ImGuiCol_Text + 1]`, 1-based), `GetWindowDrawList()` a draw list with its `Add*` methods; colours are ImU32 numbers (negative ones too, as `bit.bor` makes them), textures their pointer as a number; printf-style text (`Text`, `TextColored`, `SetTooltip`, ...) is its format alone, so `%%` shows `%`; missing or nil arguments take ImGui's defaults, extra ones are ignored, overloads go by the arguments' Lua types, and a name ImGui hasn't got is nil (addons test for functions that way). The plugin manager says the Addons plugin is interface 4.16, so addons written for both versions use 4.16's calls. 248 of the functions are generated from the SDK; overloads, text, text boxes, lists and what goes through the layout (`Begin`, `End`, `SetWindowPos`) are written by hand.
- **Fonts**, as Ashita's: Agave at 18 (the default), 24 and 32 px, each with Font Awesome 6's regular, brands and solid icons merged in (`fonts\imgui\`, SIL OFL; `[client] imgui.font` puts another font in Agave's place, the icons staying: a font file's name, looked for in `fonts\imgui\`, `fonts\`, the fonts Windows installs for one user and Windows' own, in that order, or its full path; `.ttf`, `.otf` or `.ttc`; a file that can't be loaded is logged and Agave is used; read once as the first frame makes the atlas, so it needs a restart; /vana > Client > ImGui), in one 2048x2048 texture (Ashita oversamples its glyphs 3x across, which, with every glyph snapped to whole pixels, only makes the texture 4096x4096). Fonts plugins and addons add (`AddFontFromFileTTF`) go into the same atlas, made again before the next frame.
- **Input**: a press or wheel over an ImGui window (unless it lets the mouse through, `NoMouseInputs`) is ImGui's alone: the game doesn't see it, through its messages or DirectInput, as with VanaCore's own window, and neither do Ashita addons' `mouse` events, but for the addon whose window it is (Windower's and VanaCore's addons hear it as blocked); with a popup open, a click anywhere is ImGui's (it closes the popup). While an ImGui item has the keyboard (typing in a text box), keys and characters go to ImGui, and the game's DirectInput keyboard reads no presses (releases still, so a key held before doesn't stick). Japanese input's window is placed at the text box (IME).
- **Settings**: window positions and sizes in `config\imgui.ini`. `GetVisible`/`SetVisible` hide every window (they're still built).
- **Layout** (`/vana layout`: the Addons tab's Layout page; `src/core/layout.cpp`): every addon's and plugin's window, by who draws it, with its X, Y and Scale to change. Each top-level `Begin` and `End` (Lua's and `IGuiManager`'s) goes through VanaCore, which changes where the window goes and its scale without its addon knowing. A window ImGui places (its addon gives a first place at most) is put where it was set each time it appears, and where it's dragged to after that is kept; a window its addon places every frame (`SetNextWindowPos` or `SetWindowPos` with `ImGuiCond_Always`: HUD bars, anchored windows) is moved by an offset from its addon's place, so it still follows what it's anchored to. An addon that reads back where its window went and keeps it (XIUI) takes the move as its own and the offset goes (`Layout: ... keeps ...` in the log), so nothing drifts. Scale is literal: the addon lays its window out at its own size, and at the frame's end everything the window drew is scaled from its top-left corner (its draw list and its clipping, its child windows, the popups opened from it and a tooltip over it, and what it drew on ImGui's foreground and background lists between its `Begin` and `End`, as XIUI draws its bars), text, pictures and the addon's own drawing alike (text is the font's pixels stretched). The mouse over a scaled window, as it's drawn, is given to ImGui in the window's own pixels (a press keeps that until it's let go), so hovering, clicks and dragging land where things are drawn; the mouse hook and DirectInput block the drawn rectangle. Kept in `config\layout.json`, by window name. `/vana reset ui` moves every window on the page (each addon's and plugin's ImGui windows, and their text and shapes) to the screen's top-left corner, 0,0, to find one gone off the screen (put there on a bigger screen or resolution): a window shown now moves at once, one that isn't when it next shows, and scales stay. It copies `config\layout.json` first, to `config\layout-before-reset-<date>-<time>.json` (with the game closed, renaming that `layout.json` has the layout back), and moves nothing if it can't. The game's own windows (chat, menus, compass) and the /vana window, which always stays on the screen, keep their places. Lua: `vana.layout.windows()`, `set(name, x, y, scale)`, `reset(name)`, `highlight(name)` (the window outlined; the Layout page does it for the row under the mouse).
- A plugin or addon using ImGui wrongly doesn't end the game: ImGui's failed checks are logged once each (`ImGui: check failed ...`), what one leaves open at the frame's end (a `Begin` without its `End`, a style pushed and not popped) is closed then (`ImGui: fixed at the frame's end ...`), and functions that draw do nothing outside a frame (an addon's command handler).

Tested in a test process with a stand-in FFXiMain.dll, on both renderers: a plugin built against the client's 4.16 SDK drawing every kind of widget, a table, icons and the 24 px font; the client's `VanaView` plugin's settings window (`/vv`); an addon checking the Lua conventions above; and 11 of the client's 34 ImGui addons loading and drawing without errors (`nowplaying`, `chronicle`, `itemwatch`, `chatmon`, ...). The other 23 stop before drawing on what VanaCore's Ashita layer hasn't got yet: the `d3d8` library (12 of them), the resource manager, font objects (`FrameAnchor`), `socket.core`, the inventory.

### Screenshots
`/vana abtest <setting>=<a>,<b> [seconds] [rounds]` compares two values of a `[graphics]` setting in one session (stand still): it flips the setting every 8 seconds in A B B A order (two rounds: 8 periods, about a minute), times the game's frames in each once the switch has settled (not while DLSS or frame generation are starting), then puts the setting back and echoes the result to your own chat log (only you see it; it is never sent as `/say` or anything else) and writes it to `logs\abtest-<date>-<time>.log`, kept whether or not logging is on, with the settings it ran under and each period's frames: frames a second, the average, median, 95th and 99th percentile frame time, the frames shown with frame generation, B against A, and each period's frame rate, so a drift shows. For example `/vana abtest dlss=off,on`, `/vana abtest dlss.framegen=off,2x`, `/vana abtest dlss.quality=35,100`; another section's setting as `section/key`; `/vana abtest stop` ends it early (`/abtest` works too). A frame rate limit (`fps.max`) caps what it can measure.

`/vana debug` opens (and closes) the Debug window (`addons\vanacore\vana\debug.lua`, in the /vana window's look; also Debug under its Tools), tools for finding out why something goes wrong, each on a tab under its title (Views, Collision, DLSS crash, Rings, Recording; hover one for its full name; the window is as tall as the tab shown, and the one picked stays till the game closes). **DLSS crash tests** make the DLSS helper fail at its next frame's upscale, where a real crash would come, so what one leaves can be tried: **Crash** (an access violation on the thread serving the game: the full `[VanaCore.Dlss.exe] CRASH:` report in `logs\vanacore.log` and a `dlss-crash-*.dmp`), **Other thread** (the same on a thread of its own, as a driver's would be), **C++ exception** (an unhandled one), **Fail-fast** (Windows ends it on the spot: no report, but the chat still has the code and what it was doing) and **Hang** (it stops answering with the game's frame in hand: DLSS or FSR turns off within 3 seconds and the game goes on). Each asks twice (the button says Again to run), and needs DirectX 12 with DLSS or FSR running; switching DLSS off and on starts a new helper. Lua: `vana.graphics.dlss_crash_test(kind)`, `kind` one of `crash`, `thread`, `cpp`, `fastfail`, `hang` (true, or false and why). **Shadow & AO rings** shows where the shadows' and the occlusion's rings fall (`sun_rings`, `ao_rings`) and the taps each ring takes (`16 / 12 / 8 / 6` for the shadows; the occlusion's by its Quality, `32 / 24 / 16 / 10` at Max): **Show shadow rings** and **Show AO rings** tint the picture by ring (the Debug view's 15 and 16: green every tap, then yellow, orange, and red past the third, a dark line at each edge; Hide puts the picture back), and each one's switch and spacing are there beside them, the Graphics page's own settings. **Frame recording** is the recording below, from its buttons (Record 30 s, Stop).

`/vana debug <seconds>` records that many seconds of frames one by one (5 to 120; the Debug window's Record 30 s; `/vana debug stop` ends it early): each frame's time and where it went (the game's own work, its Direct3D calls and the slowest single call, its sleeps, VanaCore's work and frame rate limit, Present; from Direct3D 12's profile, turned on for it: drawing the calls, waiting for the GPU, the swap chain, waits on the DLSS helper, GPU time, draws, uploads, pipelines made), with what the log said meanwhile. Then `logs\frames-<date>-<time>.csv` has a row a frame, and `logs\debug-<date>-<time>.log` (and briefly your own chat log, echoed: only you see it) says: the frame times' spread, what holds the frame rate (the game's own cap, `fps.max`, the GPU, or the CPU's work), the hitches (frames well over the median) with what grew in each and the log's lines around the worst (with logging on), and whether they come at a steady interval. Both files are written whether or not logging is on.

**Flickering shadows:** record (Record 30 s) while moving the camera by the shadow that flickers, and the log's `flicker watch` lines say what the shadow maps did (on Direct3D 11 too: it has no frame profile, but a recording, or `profile=1`, turns the watch on there; its recording's `shadows, the maps over the last 5 s` line is Direct3D 12's). Each map is cut through a sphere round the part of the view it covers, its radius in whole units; when the radius changes, the map's texels change size and every shadow edge in it lands on a new grid and moves a little, which is a flicker while the camera moves (the sharp map's reach follows the player's distance from the camera, so a camera pushed in or out by a wall did it: that distance is now rounded up to 3 units and held at its most of the last 10 seconds, so the radius changes only when the camera goes back past what it covers, and goes down after 10 seconds closer; if the lines still say it steps, something else moves the reach). "the sharp map's sphere went radius 23 -> 24 units" lines (with the reach, the player's distance and how far the camera moved) say it; on Direct3D 12 "the sharp map's layer was drawn again (age, moved, ...) through a sphere of radius ..." says it of the still layers, with why they were drawn again; the 5-second `shadows, the maps over the last 5 s` line has the sharp map's radius, its reach and the player's distance from the camera, least to most, and how many times each layer was drawn again for each reason; `shadows: setup` says the shadow settings and the scene's size when they change. The values the camera and the maps follow (`shadows: the sharp map's sphere radius`, `camera: moved since the frame before`) are watched for turning round and round, and `cache\trace_gfx.txt`/`flicker_gfx.txt` have them a frame (far-radius, sharp-radius, sharp-reach, player-distance, then on Direct3D 12 layers-drawn and why). The light the shadows fall from is a vote among the lit draws in view; where the sun moves with the clock, another light that gets ahead in the vote (a pillar's light a few degrees from the sun's) is kept out while the sun is still voted for, because the shadows slid to it and back as the camera panned: "a light N degrees from the clock's sun is ahead in the vote ... and is kept out" says it did, "the sun's light changed N degrees" says a change was let through. With the game's clock known, the sun (06:00 to 18:00) and the moon (the rest of the day) take turns by the clock alone, whatever the vote says: the one the clock puts up is kept while no lit draw in view uses it, and the other is never taken; "the sun (or moon) is the light the clock puts it at" says the shadows went to it.

`/vana graph` opens (and closes) a window of the game's performance over the last minute, a point every 0.5 s (the average of five samples, one every 100 ms), drawn with ImGui so it moves and resizes like an addon's window. A list (and arrows either side of it) flips between the metrics: FPS, FPS shown with frame generation, frame time, the worst frame in each point, the CPU the game uses (in cores), its private memory, and its address space (what's used, and the largest free block). The FPS line is red wherever it's under 30. Under each graph: now, the average, lowest and highest over the minute, the 95th and 99th percentile for times, and for FPS the average of the slowest 5% of points. Where each frame goes (the game's own work, its Direct3D calls, its sleeps, VanaCore's work and frame rate limit, Present) and DirectX 12's GPU time, draws and uploads are in `/vana stats`, not here: nothing in the graph costs FPS. **Pause** (at the bottom left; **Resume** while it's paused) holds the graph still, **Clear** empties it, and **Save CSV** (or `/vana graph save`) writes what it holds to `logs\graph-<date>-<time>.csv`, whether or not logging is on. FPS and frame time are counted all the time (a clock read a frame), so the window opens with the last minute already in it. `/vana graph on` and `off` open and close it, and so does the **Performance graph** button at the bottom of the `/vana` window's Client and Graphics tabs.

`/vana stats` opens (and closes) a window that says where a frame's time goes, as a tree in the way of Unreal Engine's GPU Visualizer: two stacked bars (the CPU frame and the GPU) to see the shape at a glance, then a table you open down to the single call, each line with its milliseconds a frame, its share of the frame and, where it has them, its calls a frame, averaged over half a second. **The frame (the render thread)** is split into the game's own work (what's left once the rest is taken out), its Direct3D calls (sorted into draw calls, textures, vertex and index buffers, lighting and materials, render state and transforms, shaders and render targets, each down to the calls themselves), its sleeps, **VanaCore** (its settings and chat, ImGui, Ashita plugins, **each Lua addon by name**, its graphics layer and its interface drawing), the frame rate limit and Present. **GPU (DirectX 12)** is the GPU's own time between timestamps it writes at the start of each stage: the game's scene, the sun's shadow maps, ambient occlusion, bloom, god rays, the composite (fog, shadows, colour grade, outlines), depth of field, FXAA, DLSS and the interface drawn over the scene; **Counters** are draws, uploads and pipelines made. **Pause** freezes the numbers, **Record Stats Report** starts a recording and, pressed again, stops it and writes the whole recording to `logs\stats-<date>-<time>.txt` whether or not logging is on: one file with everything, to send as it is, in sections (the PC and VanaCore: version, Windows, CPU, renderer, card and driver; the frame data; every item a column a look, as csv; the lag spikes; the shadows; the settings); `/vana stats save` writes what the window shows at any time, and nothing is timed while the window is closed. The button at the bottom of the `/vana` window's Client and Graphics tabs opens it too.

The game's own work (its logic, animation, skeletons, physics) is one line, because FFXiMain.dll has no names to time by. The recording (**Record Stats Report**; experimental, off by default, costs a little FPS) adds a view of it: a thread looks at where the render thread is about every millisecond, reads the top of its stack, and works out which of the game's functions it's inside of (the return addresses in FFXiMain.dll with a call just before them, going where a function starts: the function starts come from the Ghidra export, `addons/vanacore/vana/data/ffximain_functions.bin`). That gives four views of the same samples: **By subsystem** (below), a **Call tree** where each function shows the time of all it calls, as a profiler does (the main loop at the top, open it down to what's under it), the **Hot functions** the thread was in itself, and **By module**. Functions are `FUN_10086020`, as the Ghidra export names them, until a line in `addons/vanacore/vana/data/ffximain_labels.txt` names one (`10086020 Nameplates | Interface`) and, after the bar, puts it under a heading: **By subsystem** counts each sample for the innermost labelled function it's inside of, so naming the few functions that run animation, physics, effects or the interface makes the view say what each costs. Labels are worked out from the Call tree and the Ghidra decompile, a few at a time. GPU timing is DirectX 12's (nothing on DirectX 11 or the game's own renderer), and `/vana stats on`, `off` and `save` do what they say. While a recording runs, `vanacore.log` also gets a `Menus:` line for each of the game's windows that opens, closes or changes (its cursor, its count of buttons, the cursor the game keeps for its next opening, closing or destroyed, the window the keys go to), each arrow-key step in a menu and who answered it (the game, or VanaCore's extra rows), and each menu key or pad button with what kept it from the game, an addon by name; a value that can't be right is marked `!` (a cursor with no button under it, a window whose owner points at another). That's for stuck-menu reports: record while it happens, then send the log (`src/core/menulog.cpp`).

For shadow reports, a recording also records the shadows (DirectX 12) for the report's Shadows section (written to `logs\stats-shadows-<date>-<time>.csv` while it runs, then taken into the report and deleted when it stops, as are the lag spikes' `stats-dips-*.txt`): a line every frame with the sun's shadows as they were. It holds the scene the shadows were handed (the Vana'diel clock, indoors, the night, the light picked and its colour, the ambient, the player, the camera, the projection with DLSS's jitter) and the light they fell from after the dusk clamp, dawn and tilt. It has how strong they were (the cloud's share, the room, the ease in) and each map's cascade (its centre, texel, size, snap, a hash of its matrix, and whether a still layer was used). It counts the casters drawn and those left out (no pipeline yet, no room for their uniforms), with the cache, the caster pass and the zone's own meshes, and the effects' state. Every `[graphics.effects]` key is listed at the top, with a line for each one changed while it ran. It stops at 40 MB (about 25 minutes at 60 fps) and says so. Every report's Settings section has every setting VanaCore had in force, defaults included. That's each key `vanacore.example.ini` lists, set or its default, then any other key the settings file sets. The account's name, password and tokens are left out (`src/core/stats_shadows.hpp`, `src/gfx/gfx_sun_record.h`).

Print Screen (while the game is in front) or `//screenshot` saves a PNG of the game to `screenshots\<yyyy-mm-dd>\<character>_<yyyy.mm.dd>_<hhmmss>.png` next to `VanaCore.exe` (`screenshot_...` before logging in), and the chat log says where. `//screenshot hide` leaves out VanaCore's own drawing (the label, the FPS counter, addons' text), `//screenshot show` keeps it; Print Screen and plain `//screenshot` follow `vanacore.ini`:
```ini
[screenshots]
overlays=1          ; 0 leaves VanaCore's drawing out of Print Screen's screenshots (default 1)
```
The frame is copied on the game's thread and written by another, so taking one doesn't hitch the game. Print Screen is an ordinary key bind (`/bind printscreen /screenshot`, as Ashita has `SYSRQ`), so `/unbind printscreen` turns it off and `/bind printscreen <command>` gives it another job; it works with the chat line open. Windows' own screen capture (the Snipping Tool) may open over the game as well: VanaCore no longer hooks the key to keep it from Windows.

F11 hides the game's interface for a clean view (or a screenshot) and shows it again: the game's own hide mode, so its windows, the chat log and the bars go and the world and the names over heads stay. VanaCore's drawing goes with it (the label, the FPS counter, addons' text and ImGui windows, Ashita's fonts). As in the game it works in the world only, and Escape or a cutscene brings the interface back. A `/bind` on the key comes first, and the game doesn't see it:
```ini
[ui]
hide.key=f11        ; a key's name as /bind takes it (f11, scrolllock, numpad0, ...), or off (default f11)
```

### MCP server (AI tools)
With `[mcp] enabled=1` (the /vana window's **Client > AI MCP > MCP server**, off by default; its **Server** line says whether it's listening and which client used it last) VanaCore runs an MCP server (Model Context Protocol, its Streamable HTTP transport) inside the game, so an AI tool on this machine sees the running client from the inside and works in it live: Claude Code connects with
```
claude mcp add --transport http vanacore http://127.0.0.1:47800/mcp
```
```ini
[mcp]
available=0 ; 0 turns the feature off for good: the server never starts, whatever enabled says, and the /vana window
            ; has no AI MCP rows. For servers that don't want AI tools in their players' games. Default: 1
enabled=1   ; off by default; turning it on or off takes effect within 2 seconds, without a restart
port=47800  ; the next free one (up to +9) if another game has it; the log and the chat log say which
token=      ; when set, clients must send "Authorization: Bearer <token>"
```
It listens on 127.0.0.1 only, answers only requests whose `Host` is its own, refuses any a web page sends (an `Origin` that isn't this machine's, a body that isn't JSON), and says in the chat log when it starts and when a client connects. Each connection (an MCP `initialize`) is a numbered session, so the chat log says which chat is probing: `MCP: #3 claude-code connected`, then `MCP: #3 claude-code is "alliance list RE"` once the chat has named itself with the `hello` tool (the server's instructions ask every chat to, before its first other tool; a client can also name itself in its `clientInfo.title`). The session's id goes back as the `Mcp-Session-Id` header and the client sends it with its later requests (a script that keeps it needs no new `initialize` on each run; one that sends none counts as the newest session); a `DELETE` with it ends the session (`MCP: #3 ... left`). The /vana window's **Chats** line lists the sessions used most recently, and `vana.mcp.info().sessions` has them all. Its tools (`src/core/mcp_tools.cpp`):

| Tool | What it does |
|------|-------------|
| `hello` | Names the chat to the player: a few words for its topic, shown as `#n "name"` in the chat log and the /vana window |
| `game_state`, `entities` | The character, target, party, buffs, and every entity nearest first (with each one's address); where the game keeps those structures |
| `read_memory`, `write_memory` | A hex dump, typed values, pointers (each with what it points at) or a Shift-JIS string; writes bytes, text or a value, code included |
| `disassemble` | x86, Intel syntax (`src/core/disasm.cpp`: integer, x87, MMX, 3DNow!, SSE/SSE2; checked against capstone over all of FFXiMain.dll), with system functions named and globals' values and strings shown |
| `modules`, `find_pattern`, `search_memory` | The DLLs and their sections; signature scans; strings (as the game stores them), bytes or values anywhere in memory |
| `find_references` | Calls, jumps, instructions and data pointers that refer to an address |
| `value_scan` | Cheat Engine's first scan and next scan (changed, increased, between ...), to find where a value lives |
| `watch` | The CPU's 4 hardware breakpoints, without stopping the game: which instruction wrote, read or ran an address, how often, with the registers and the code addresses on the stack (for code, each caller and its arguments) |
| `packets`, `inject_packet` | The last 4,000 packets each way after decryption, or one id's last in full; adds a packet to the next buffer |
| `chat_log`, `run_command` | The last 2,000 chat log lines; runs a line as typed and returns the lines that followed |
| `lua` | LuaJIT in the game, on its thread, with VanaCore's addon API and FFI (to call the game's functions), in a state of its own (`addons/vanacore/mcp`) |
| `screenshot` | The game's screen as a picture |

Every address argument is an expression: `[[FFXiMain.dll+0x4A1234]+0x10]+4` (numbers are hex, `#12` is decimal, `[x]` reads a pointer), `ghidra(0x10123456)` for an address from a disassembly of the file when FFXiMain.dll is loaded elsewhere, and `entities`, `party`, `player`, `target` for the game's structures. Results name addresses as `FFXiMain.dll+0x1234` with the file's address beside them. Memory is read with `ReadProcessMemory`, so a bad address is an error and not a crash; what belongs to the game's thread (its structures, Lua, the command line, the screen) runs there at the next frame.

### Fonts and icons
Fonts in `fonts\` next to `VanaCore.exe` are loaded into the game process when it starts (`.ttf`, `.otf`, `.ttc`, and `.woff`/`.woff2`, unpacked with DirectWrite; nothing is installed in Windows), so any text in the game drawn with GDI can use them by name: VanaCore's overlay, its addons' `vana.ui.text`, and plugins' and Ashita or Windower addons' font objects. The log lists them (`Fonts: ... loaded ("<family>")`). VanaCore ships Google's Material Symbols Outlined (weight 400, unfilled, the icons on fonts.google.com/icons). An icon is a character of it: VanaCore addons find it by name with `vana.ui.icon('undo')`; plugins and other addons draw its code point (shown on the icon's page, `undo` is U+E166) in the font `Material Symbols Outlined`, not bold. VanaCore reads the names from the font's own ligatures (`Fonts: 4267 icons in "Material Symbols Outlined"`).

### Copy and paste
While the chat line is open, Ctrl+V types the clipboard's first line into it (up to the line's 120 bytes, converted to FFXI's Shift-JIS, Japanese included), and Ctrl+C copies what's typed so far to the clipboard (without colour codes or auto-translate phrases). With the chat line closed, both keys do what they did before. VanaCore finds the chat line in FFXiMain.dll on the first frame (the global at FFXiMain.dll+0x62E0A0; the line's state at +0xF108, its text at +0x84F4, its length at +0x86B8) and takes over the game window's messages for the keys (`Window: ...` in the log).

#### Addon packages (.vcaddon)

An addon can come as one `.vcaddon` file (a zip of its folder and an `addon.json`). Double-clicked on Windows, dropped in
`addons\install\`, or picked with /vana > Addons > **Install from file** (`/vana install [file]`), it shows its name,
version, author, description and where it came from, with the warning that an addon is a program, and is installed into
`addons\vanacore\<name>\` only on a yes: **Install and load**, **Install only** or **Not now**, and **Load at every start**
(its `scripts\boot.txt` line). A package never replaces VanaCore's own addons or a folder it didn't install, and an
update keeps the old folder in `backups\addons\`. `tools/vcaddon/pack.py` makes one; the format and the checks are in
[tools/vcaddon/README.md](../tools/vcaddon/README.md).
